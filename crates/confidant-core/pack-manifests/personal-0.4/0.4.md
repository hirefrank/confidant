# Personal schema pack 0.4

The **implicit** built-in personal pack for spec 0.4: every 0.4 vault has it,
whether or not `confidant.toml` lists it, and a `personal@…` entry in `packs`
is a no-op. Vaults on spec 0.1–0.3 keep the frozen `personal@0.2`
([`0.2.md`](0.2.md)); `personal@0.3` ([`0.3.md`](0.3.md)) is frozen and no
spec selects it. The vault `spec` selects the active built-in version.
Compiled into the `confidant` binary as a built-in **declarative** pack
(#550): its bytes ship inside the binary and are loaded through the same
manifest-v3 / declarative path external packs use (ADR-8). A vault may list it
alongside any external pack; each pack owns its own verbs, fields, edge kinds,
and check rules, and folds the ledger independently (#177).

The machine-readable source of the pack's claims is
[`manifest.toml`](manifest.toml) (spec `spec/pack-manifest.md`). Because the
bytes are loaded from **compiled-in** origin, the pack is trusted as core
(#504 decision 3): its rules name the stable finding codes directly and it may
claim the core `touch` verb. The allowance is keyed on the bytes' origin,
never the pack name, so a vault directory `packs/personal@…` still fails
`E_PACK_INVALID` (#504 R8, #551).

`personal@0.4` keeps every `personal@0.3` claim: the person fields and
relationship edges, places and things, the `touch` verb, and the
cadence/date rules. It adds cadence semantics (a basis, a mode note, and an
explicit "none, by design"), richer touches (an optional duration and a
1:1-vs-group mode), and the person-story fields — the one-line
`relationship_context`, the `role_history` timeline, the typed
`alias_history`, per-fact provenance, and the operator's `human_note`. The
change is additive; there is no record rewrite. The
earlier breaking changes still apply: `relationship_to_me` is renamed to
`relationship`; `cadence` accepts `never`; `birthday`/`dates`/`cadence`/
`relationship` are re-expressed declaratively; and the touch-kind list drops
`coffee` (use `meal`).

The one-sentence product framing: **people you know, places that matter,
things you're working on or care about, and the moments that connect them.**

## Record types

`personal@0.4` keeps the two record types `personal@0.3` introduced. The
promotion rule is deliberate: a place or thing earns a record when another
record needs to point at it, when it has its own relationships, or when it
needs a stable name in the roster. Otherwise it stays a note.

| Type | Prefix | Collection | Main file | Required | Optional |
|---|---|---|---|---|---|
| `place` | `pl` | `places/` | `place.md` | `name`, `kind` | `address`, `tags`, `links` |
| `thing` | `th` | `things/` | `thing.md` | `name`, `kind` | `tags`, `links` |

Both are entities: they can be edge endpoints and `context` targets, and can
be named by `entity:` on a note or interaction. They are not person-like:
they have no aliases, cadence, touchpoints, or person-shaped context view.
Both are roster-visible and use `no_ai = "full"`; `no_ai: notes` is not
available for them.

### `place`

A location worth referring to again: a home, workplace, recurring venue,
neighborhood, or city. `kind` is required and suggests `home`, `work`,
`venue`, `neighborhood`, `city`, or `other`. `address` is free text; it is
never geocoded or parsed. Coordinates and structured postal fields are out
of scope; use `links` or the body.

### `thing`

A project, object, work, idea, vehicle, book, or tool worth referring to
again. `kind` is required and suggests `project`, `object`, `work`, `idea`,
`vehicle`, `book`, `tool`, or `other`. A company is an `org`, not a thing;
a one-off event is an `interaction` or a note.

### `kind`

`kind` is one primary noun per record, not a free-form tag soup. It is a
required `non-empty-string`; the vocabulary above is documented and enforced
by the capture skill, not by a closed grammar. `tags` is the cross-cutting
label (`tags: [house-history, renovation]`).

### When a thing is a note

Use a note instead when the fact is dated, sensitive, or owned by exactly one
person/place and never referenced elsewhere. A note carries its own date and
`no-ai`, so it does not bypass note-level privacy. There is no `notes:` or
`serial:` field; standing prose goes in the body, and one-off identifiers go
in the body or a note.

## Fields

This pack owns optional flat front-matter fields on `person` records and the
declared fields on its `place`/`thing` records (spec §8). A value that does
not match its grammar is `E_FRONTMATTER`.

| Field | Grammar | Meaning |
|---|---|---|
| `title` | non-empty string | Job title. |
| `company` | non-empty string | Employer. |
| `location` | non-empty string | Free text; not geocoded. |
| `emails` | list | Contact emails. No syntax validation or normalization. |
| `phones` | list | Contact phone numbers. No parsing or normalization. |
| `links` | labeled list | `LABEL:VALUE` profiles (for example `linkedin:https://…`). |
| `tags` | list | Free-form labels; `/` expresses hierarchy. |
| `birthday` | `YYYY-MM-DD` or `--MM-DD` | Date of birth. |
| `dates` | comma-separated `LABEL:DATE` | Other recurring dates. |
| `relationship` | non-empty string | How the person relates to the operator (the category: `friend`, `mentor`, `investor`). |
| `relationship_context` | non-empty string | The one-line story of how you know them; distinct from `relationship` (see below). Private context. |
| `role_history` | `PERIOD\|ROLE\|COMPANY[\|SOURCE]` list | The role/company timeline; `title`/`company` stay the current values. Private context. |
| `alias_history` | `KIND\|VALUE\|STATUS[\|SOURCE]` list | The typed alias ledger; the plain contact lists stay the current values. Private context. |
| `profile_provenance` | `KEY\|SOURCE\|DATE` list | Where each enriched profile fact came from and when; the newest date wins. Private context. |
| `human_note` | non-empty string | The operator's own words; agents never edit it. Private context. |
| `cadence` | `<N>d` or `never` | Keep-in-touch interval; `N` is `1..=3650`. |
| `cadence_basis` | non-empty string | Why this cadence: `observed` or `intention` (see below). |
| `cadence_note` | non-empty string | Why the cadence or its mode changed; private context. |
| `snooze_until` | `YYYY-MM-DD` | One-off snooze date for the cadence nudge. |
| `kind` | non-empty string | Primary noun for a place or thing. |
| `address` | non-empty string | Free-text place address; private context. |

Lists are comma-separated, optionally wrapped in one `[...]`; entries are
trimmed, non-empty, and unique. A labeled-list splits at the first `:`,
`LABEL` matches `[a-zA-Z0-9_-]+`, and the value is trimmed, non-empty and may
contain `:`.

### `relationship` vs `relationship_context` (#742)

`relationship` is the **category**: how the person relates to the operator in
one noun (`friend`, `mentor`, `investor`, `former manager`). It is stable,
short, and the thing an edge or a filter can compare.

`relationship_context` is the **story**: one line that answers "how do I know
them" for someone reading the record cold — "I'm an investor in her
company"; "she was my boss at two startups". It is prose, it can go stale,
and enrichment rewrites it when the relationship changes. Keeping both means
a filter can use the category while a human or agent gets the sentence,
without parsing one out of the other. Capture asks for the story once, when
the person is added; enrichment targets the field instead of editing the
profile body.

### `role_history` (#740)

`title` and `company` are the **current** values. `role_history` is the
timeline, one chapter per entry:

```
role_history: [2019-2021|Product manager|Example Co|linkedin-export, 2021-|Founder|Example Studio]
```

Fields are pipe-separated: `PERIOD|ROLE|COMPANY[|SOURCE]`.

- `PERIOD` is `YYYY-YYYY`, or `YYYY-` for a chapter still open (the period
  is required, so the trailing `-` keeps the field count unambiguous).
- `ROLE` and `COMPANY` are free text and may contain spaces, but not `|`.
- `SOURCE` is optional provenance (`linkedin-export`, `operator`, …).

Enrichment appends a chapter instead of overwriting the old one, so the arc
survives. Update `title`/`company` at the same time to keep the current
values true. A period with the start after the end, a malformed year, a
missing field, or a repeated entry is `E_FRONTMATTER`.

### `alias_history` (#739)

`emails`, `phones`, and `links` are the plain **current** values and stay the
primary contract (and what `alias add`/`context.aliases` use). `alias_history`
is the typed ledger that says which value is live, which is kept for
archaeology, and where each came from:

```
alias_history: [email|ada@example.test|current|email-signature, email|ada@old.example.test|historical|linkedin-export]
```

Fields are pipe-separated: `KIND|VALUE|STATUS[|SOURCE]`.

- `KIND` is `email`, `phone`, `handle`, or `name`.
- `VALUE` is the address, number, handle, or former display name. It may
  contain `:` (a URL handle) but not `|`.
- `STATUS` is `current` or `historical`. A live value goes in the plain
  contact list; add a typed `current` entry when you also know its source. A
  value that no longer works is `historical`.
- `SOURCE` is optional provenance.

`alias resolve` reads both the plain values and the typed entries, matched
by kind, and **prefers current over historical**: a live address wins over
an old one, so an archaeological entry never shadows the one to use now. A
malformed entry is `E_FRONTMATTER` and matches nothing.

### Profile provenance (#738)

Enrichment is only trustworthy if a fact can say where it came from and
when. `profile_provenance` is one map-style list for the profile facts:

```
profile_provenance: [title|linkedin-export|2026-03, company|linkedin-export|2026-03, profile|linkedin-export|2026-03, relationship_context|operator|2026-10]
```

Entries are `KEY|SOURCE|DATE` (comma-separated, optionally wrapped in `[...]`):

- `KEY` names the fact: `profile` for the body text, or a declared field
  name (`title`, `company`, `location`, `links`, `relationship`,
  `relationship_context`, `human_note`, …). Keys match
  `[a-z][a-z0-9_]{0,40}`; a well-formed key with no matching fact is inert.
  The grammar validates the shape, not membership, so adding a field later
  needs no grammar change.
- `SOURCE` is where the fact came from (`linkedin-export`, `operator`,
  `email-signature`, …).
- `DATE` is `YYYY-MM`: a fact is aged at month precision.

A repeated key is allowed and records a newer chapter of the same fact.
**The newest date wins**: `context` returns one effective entry per key, so a
stale import can never shadow a fresher enrichment. Two entries for the same
key and date are `E_FRONTMATTER` (a tie has no winner), as is any malformed
entry. Update the entry when you update the fact; the older entries stay on
disk as history.

### Profile authorship (#751)

The profile body is the **agent-maintained summary**. The operator's own
words live in `human_note`:

```
human_note: The kitchen-table pitch is the part I remember.
```

- `human_note` is the operator's field. **Agents never edit it** — this is
  capture policy in the pack skill, not code enforcement, so an agent that
  follows the skill leaves the operator's words verbatim.
- Agent-written paragraphs in the body lead with a dated marker:
  `Enrichment, 2026-10: Met at Example Conf; two meetings since.` The date
  is the month the paragraph was written or refreshed; the marker stays in
  the body, so it survives `record edit` replacing the file.
- Human paragraphs in the body (legacy text, or words the operator pasted)
  carry no marker and are preserved verbatim.
- When enrichment rewrites the summary, update the `profile` entry in
  `profile_provenance` at the same time, so the body says who wrote it and
  when.

`context` shows both: `entity.profile` (the body) and the pack view's
`human_note`. Neither is private from the operator, and both follow the
`no-ai` and `--exclude-private` rules.

### Cadence semantics (#750)

A cadence is a claim about the future, and the schema now records where the
claim came from and what it assumed.

- **Basis.** `cadence_basis` says whether the interval is an observed rhythm
  (derived from the touch history) or an intention (the rhythm the operator
  wants). It is a documented, open vocabulary — `observed` and `intention`
  are the values the capture skill writes — for the same reason
  place/thing `kind` is open: a new honest value should not need a spec
  change. `context` shows it under its declared name. `touch` history and
  `last_touch` remain the only observed facts; the basis records which one
  the cadence is.
- **Mode note.** `cadence_note` records the mode a cadence was set for and
  why it changed ("frequent 1:1s through 2024; investor updates since
  2025"). When the relationship changes shape, revisit the cadence instead
  of silently keeping a window that no longer describes the relationship.
- **None, by design.** `cadence: never` is the explicit "none" state,
  distinct from an unset `cadence`. It means the operator considered the
  relationship and chose no nudge; an unset field means no cadence has been
  chosen. `context` marks the deliberate state with `cadence_never: true`,
  and `W_CADENCE_OVERDUE` never fires for it. Pair it with
  `cadence_basis: intention` to make the intent explicit.

`cadence_basis` and `cadence_note` are metadata about the cadence; they do
not change the number. Only `cadence` drives the nudge.

`snooze_until` suppresses `W_CADENCE_OVERDUE` while `as_of < snooze_until`
(the person is eligible again on the snooze date; a past date has no effect).
Only the canonical person's own record is read.

## Edge kinds

Core ships `married`, `introduced`, and `colleague`; `personal@0.4` keeps the
0.2 kinds: symmetric `friend`, `family`, `sibling`, `partner`, and directed
`parent` (`a` is the parent of `b`) and `mentor`. It keeps the four directed
kinds `personal@0.3` added:

| Kind | `a` | `b` | Meaning |
|---|---|---|---|
| `visited` | `person` | `place` | Durable "has been to". |
| `lives_at` | `person` | `place` | Residence; `since` / `until`. |
| `owns` | `person` | `thing` | Ownership; `since` / `until`. |
| `located_at` | `thing` | `place` | Physical location; `since` / `until`. |

`visited` is deliberately durable: a second visit is not a second edge, and
the same ordered pair is `E_DUPLICATE_EDGE`. Individual visits are
interactions or notes attached to the place. `located_at` is only for
physical things; a project is not "located" at a place, so use a note or
interaction instead. A symmetric kind must not appear twice for the same
unordered pair (`E_DUPLICATE_EDGE`); a kind no core or enabled pack claims is
`E_UNKNOWN_EDGE_KIND`.

An edge is visible to agents only when its kind's pack is in scope, both
endpoints are cleared, and the edge's own `no-ai` is not `true`. A
`no-ai: true` place or thing hides every edge touching it while the person
stays visible.

## Verbs

### `touch`

```
DATE touch PERSON-ID call|text|email|meet|meal|event|gift|video|other [note:NOTE-ID] [src:PROVENANCE] [duration:<N>m] [mode:one-on-one|group]
```

Records a touchpoint: called, texted, emailed, met, had a meal with, attended
an event with, gave a gift to, had a video call with, or other. The kind is a
closed list; a kind outside it, a missing kind, a misplaced argument or a
duplicate pair is `E_TOUCH_MALFORMED` (a core code). The core mirrored shape
is accepted too:

```
DATE touch PERSON-ID [kind:KIND]
```

`note:NOTE-ID` links a note that belongs to the touched person (after merge
canonicalization): an invalid note ID is `E_INVALID_ID`; a `note:` that is not
a note record is `E_WRONG_ID_TYPE`; a missing note, or one belonging to
another person, is `E_UNKNOWN_RECORD`. `src:PROVENANCE` records provenance;
duplicate `src:` values are `E_DUPLICATE_SRC` (core).

#### Rich touches (#741)

Two optional pairs describe the touch, not the relationship:

- `duration:<N>m` — how long it lasted, in minutes (`duration:60m`; the
  shared duration syntax also accepts `1h` and `1h30m`). A 60-minute session
  is now a fact on the line instead of prose in a note. The value must be at
  least one minute.
- `mode:one-on-one|group` — whether the touch was a 1:1 (`one-on-one`) or a
  gathering (`group`). A birthday game night and a coffee catch-up no longer
  read identically to a days-since-touch ranking, so backfilled history is a
  rule, not a judgment call.

Both are optional and independent of the kind. They are display/derived
metadata: they never change `W_CADENCE_OVERDUE`, and two `touch` lines with
the same person, date, and kind are still the same touchpoint for
idempotency even when their duration or mode differ (spec §6). A malformed
`duration:` or `mode:` value is `E_TOUCH_MALFORMED`.

## Rules

Both rules are warning-level nudges: they surface what to do next and never
block a write or a commit (#183). Each is configurable
through `[checks]`.

### `W_CADENCE_OVERDUE`

Default severity `warning`; key `personal.cadence_overdue`
(`"warning" | "error" | "off"`).

Fires for a person with `cadence: <N>d` who has no touchpoint on or after
`as_of - N` days (inclusive) and on or before `as_of`. A touchpoint is a
`touch` or `session` ledger line for that person, after merge
canonicalization. `cadence: never` ("none, by design") and an active
`snooze_until` skip the person. `cadence_basis` and `cadence_note` do not
affect the rule. `as_of` comes from `--as-of`, else `[checks].as_of`, else
today's UTC date.

### `W_DATE_UPCOMING`

Default severity `warning`; key `personal.date_upcoming`
(`"warning" | "error" | "off"`); window `personal.date_upcoming_days`
(default `7`, cap `3650`).

Fires when a person's `birthday` or an entry in `dates` has its next
occurrence within `0..=personal.date_upcoming_days` days of `as_of`. A
year-less `--MM-DD` value is the next `MM-DD` on or after `as_of`.

## Privacy and scoping

The pack honours `no-ai` on person records (`true`, `false`, or `notes`): a
`no-ai: true` person is excluded from `find`, `context`, and agent output,
while a `no-ai: notes` person stays visible but their notes and interactions
default to hidden (spec §13). PII fields (`location`, `emails`, `phones`,
`links`, `tags`, `birthday`, `dates`, `relationship`, `cadence_note`,
`relationship_context`, `role_history`, `alias_history`, `human_note`,
`profile_provenance`, and a place's `address`) are stripped from
`context --exclude-private`; `cadence`, `cadence_basis`, `cadence_days`,
`cadence_never`, `kind`, and touch metadata stay. The derived cadence state (`cadence_days`, `cadence_never`) is kept for
an uncleared person, exactly like `cadence_days` was before; `cadence_note`
is free text and stays hidden.

Places and things use `no_ai = "full"` only: `no_ai: true` hides the record
and every edge touching it, while `no_ai: false` keeps it visible. There is
no `no_ai: notes` mode for them. An uncleared place or thing returns no agent
`context` bundle at all, not an empty one, because unlike a person there is no
derived ledger metadata that justifies revealing its existence. The operator
path still returns the bundle with the badge.

Per-pack scoping (#178) applies: `--packs personal@0.4` limits agent reads to
core and personal-owned items in a 0.4 vault; a `personal@0.3` or
`personal@0.2` listing is still a no-op alias and scopes to the active
built-in. The `context` view exposes a non-person-like entity's declared
fields in `entity.fields`; the agent path only sees a cleared record.

Use fake data (`Ada Example`, `Bea Demo`, `Example Studio`, `Example
Bicycle`, fake ULIDs) in tests, fixtures, and examples. Never commit real
contact details.
