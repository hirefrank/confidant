# Personal schema pack 0.1

Declared in a vault as `packs = ["personal@0.1"]`. Compiled into the
`confidant` binary in v0 (ADR-8). This file is the pack contract. A vault
may list it alongside `coaching@0.1` (`packs = ["coaching@0.1",
"personal@0.1"]`); each pack owns its own verbs, fields, edge kinds, and
check rules, and folds the ledger independently (#177). No claim overlaps a
core verb, so the two packs coexist (spec §8).

The machine-readable source of the pack's claims is
[`manifest.toml`](manifest.toml) (spec `spec/pack-manifest.md`): verbs,
fields, edge kinds, finding codes, `[checks]` keys and message templates
all live there. This file documents the contract in prose; the folds and
findings logic stay in Rust.

Personal types are not core. A vault without this pack keeps core people,
orgs, deals, interactions, notes, aliases, merges, stages, and the generic
`touch` mirrored touchpoint, but has no `birthday` field interpretation, no
relationship edge kinds beyond core, and no cadence or upcoming-date
warnings.

## Fields

This pack owns four optional front-matter fields on any `person` record.
They are flat names (spec §8); a `birthday` on a non-person record is
unattributed and ignored. A field value that does not match its grammar is
`E_FRONTMATTER`.

| Field | Grammar | Meaning |
|---|---|---|
| `birthday` | `YYYY-MM-DD` or `--MM-DD` | Date of birth. The `--MM-DD` form is a year-less birthday (the year is unknown or deliberately unrecorded). |
| `cadence` | `<N>d` | Desired keep-in-touch interval in days. `N` is a positive integer `1..=3650` (for example `30d`, `90d`). |
| `relationship_to_me` | optional non-empty string | How this person relates to the operator (for example `friend`, `sibling`, `mentor`, `family`). The empty string is `E_FRONTMATTER`. |
| `dates` | comma-separated `LABEL:DATE` entries | Other recurring dates (for example an anniversary). |

`dates` values may be bare or wrapped in a single bracketed list:

```
dates: anniversary:2020-06-15, graduation:--05-20
dates: [anniversary:2020-06-15, graduation:--05-20]
```

`LABEL` matches `[a-zA-Z0-9_-]+`. `DATE` is `YYYY-MM-DD` or `--MM-DD`. A
malformed entry — an empty label, a label outside that character set, a
missing `:`, or a malformed date — is `E_FRONTMATTER`. Whitespace around
entries and commas is allowed; an empty `dates:` value is `E_FRONTMATTER`.

A year-less `--MM-DD` birthday or date has no year, so its next occurrence
is the next `MM-DD` on or after `as_of` (see the upcoming-date rule below).

## Edge kinds

`edge` records are core (spec §4, #179). This pack extends the closed kind
list. Core ships `married`, `introduced`, and `colleague`; `personal@0.1`
adds:

| Kind | `symmetric` |
|---|---|
| `friend` | true |
| `family` | true |
| `sibling` | true |
| `partner` | true |
| `parent` | false |
| `mentor` | false |

A symmetric kind must not appear twice for the same unordered pair
(`E_DUPLICATE_EDGE`); a directed kind reads from `a` to `b` and may appear
in both directions. `parent` is directed (`a` is the parent of `b`), not a
synonym for `family`. A `kind` no core or enabled pack claims is
`E_UNKNOWN_EDGE_KIND`; a kind owned by a registered pack that is not enabled
is `W_PACK_ORPHAN` (spec §8).

An edge carries no body (`E_FRONTMATTER`) and no `no-ai` (`E_FRONTMATTER`),
exactly as in core.

## Verbs

### `touch`

```
DATE touch PERSON-ID call|text|coffee|gift|meet [note:NOTE-ID] [src:PROVENANCE]
```

Records a lightweight touchpoint with a person: the operator called, texted,
had coffee with, gave a gift to, or met them on `DATE`. The kind is a
**closed list** — `call`, `text`, `coffee`, `gift`, `meet` — chosen so the
plaintext ledger line leaks no more than a session line does (#227 Q1). A
kind outside the list, a missing kind, or an argument in the wrong position
is `E_TOUCH_MALFORMED`.

Rich, multi-person events stay in core `interaction` records. The pack also
accepts the core mirrored touchpoint shape:

```
DATE touch PERSON-ID [kind:call|text|coffee|gift|meet]
```

which is what `record add` writes: one line for an interaction's primary
`person:` and one per `with:` participant (spec §6), so a logged interaction
counts as contact for everyone on it. This form records contact without
naming who met whom. A line with more than one `kind:` pair is
`E_TOUCH_MALFORMED`.

`note:NOTE-ID` links a note that belongs to the touched person (after merge
canonicalization). An invalid note ID is `E_INVALID_ID`; a `note:` that is
not a note record is `E_WRONG_ID_TYPE`; a missing note, or a note belonging
to another person, is `E_UNKNOWN_RECORD`. These integrity checks always run,
independent of severity config and `--as-of`. `src:PROVENANCE` records
provenance (`src:transcript/t-…`, `src:portal/evt-…`); duplicate `src:`
values are `E_DUPLICATE_SRC` (core, spec §6).

A `touch` line requires a `p-` ID (`E_WRONG_ID_TYPE` otherwise). A
well-formed `p-` ID with no record is `E_UNKNOWN_RECORD`.

CLI command:

```
confidant log touch <person> <kind> [--note <text>] [--date YYYY-MM-DD] [--src <token>] [--fallback-inbox]
```

`--note <text>` creates and links an encrypted note (as `log session
--note` does); `--fallback-inbox` queues the note to the `inbox` branch
when the keychain fails, instead of failing closed (#213).

## Cadence and upcoming dates

Both rules are **warning-level nudges**: they surface what to do next and
never block a write, a commit, or an inbox merge (#183). Each is
configurable through `[checks]` and can be promoted to `error`, demoted to
`warning`, or turned `off`.

### `W_CADENCE_OVERDUE`

Default severity: `warning`. Key: `personal.cadence_overdue`
(`"warning" | "error" | "off"`).

Fires for a person with `cadence: <N>d` who has no touchpoint on or after
`as_of - N days` (inclusive) and on or before `as_of`. A touchpoint exactly
`N` days ago is inside the window; `N + 1` days ago is overdue.

A touchpoint is any of:

- a `touch` ledger line for that person;
- a coaching `session` ledger line for that person — a coaching session
  with a client who is also a friend counts as contact (#227 Q2);
- an `interaction` record whose primary `person:` is that person, or that
  lists them in `with:`, dated on or before `as_of`.

All are evaluated after merge canonicalization: a touch recorded against a
merged-away ID counts toward the canonical person. `as_of` comes from
`--as-of`, else `[checks].as_of`, else today's UTC date.

### `W_DATE_UPCOMING`

Default severity: `warning`. Key: `personal.date_upcoming`
(`"warning" | "error" | "off"`). Look-ahead window:
`personal.date_upcoming_days`, default `7`, cap `3650` (validated like the
coaching day counts).

Fires when a person's `birthday` or an entry in `dates` has its next
occurrence within `0..=personal.date_upcoming_days` days of `as_of`. A
dated `YYYY-MM-DD` occurrence is upcoming on its month/day in the current
or next year; a year-less `--MM-DD` occurrence is the next `MM-DD` on or
after `as_of`. `as_of` resolves exactly as for the cadence rule.

## Privacy and scoping

This pack honors `no-ai` on person records (`true`, `false`, or `notes`).
A `no-ai: true` person is excluded from `find`, `context`, and any agent
output. A `no-ai: notes` person stays visible to agents — so
`relationship_to_me`, `cadence`, and upcoming dates reach `find`/`context` —
while their notes and interactions default to hidden. `no-ai` covers records
and IDs, not free-text name mentions (spec §13).

Per-pack scoping (#178) applies: `--packs personal@0.1` limits agent reads
to core and personal-owned items, so a coaching-scoped agent never sees
personal notes. Personal-owned fields, `touch` lines, and personal edge
kinds are visible only when the pack is in scope.

There is no name-only lookup and no contact import in 0.1. Use fake data
(`Ada Example`, `Bea Demo`, fake ULIDs) in tests, fixtures, and examples.
