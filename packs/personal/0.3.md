# Personal schema pack 0.3

The **implicit** built-in personal pack for spec 0.4: every 0.4 vault has it,
whether or not `confidant.toml` lists it, and a `personal@…` entry in `packs`
is a no-op. Vaults on spec 0.1–0.3 keep the frozen `personal@0.2`
([`0.2.md`](0.2.md)); the vault `spec` selects the active built-in version.
Compiled into the `confidant` binary as a built-in **declarative** pack
(#550): its bytes ship inside the binary and are loaded through the same
manifest-v3 / declarative path external packs use (ADR-8). A vault may list it
alongside any external pack; each pack owns its own verbs, fields, edge kinds,
and check rules, and folds the ledger independently (#177).

The machine-readable source of the pack's claims is
[`manifest.toml`](manifest.toml) (spec `spec/pack-manifest.md`). Because the
bytes are loaded from **compiled-in** origin, the pack is trusted as core
(#504 decision 3): its rules name the stable finding codes directly and it may
claim the core `touch` verb. The allowance is keyed on the bytes' origin,
never the pack name, so a vault directory `packs/personal@…` still fails
`E_PACK_INVALID` (#504 R8, #551).

`personal@0.3` keeps every `personal@0.2` claim: the person fields and
relationship edges, the `touch` verb, and the cadence/date rules. It adds two
entity types, `place` and `thing`, plus their fields and four edges. The
change is additive; there is no record rewrite. The 0.2 breaking changes from
0.1 still apply: `relationship_to_me` is renamed to `relationship`; `cadence`
accepts `never`; `birthday`/`dates`/`cadence`/`relationship` are re-expressed
declaratively; and the touch-kind list drops `coffee` (use `meal`).

The one-sentence product framing: **people you know, places that matter,
things you're working on or care about, and the moments that connect them.**

## Record types

`personal@0.3` is the first personal manifest that declares record types. The
promotion rule is deliberate: a place or thing earns a record when another
record needs to point at it, when it has its own relationships, or when it
needs a stable name in the roster. Otherwise it stays a note.

| Type | Prefix | Collection | Main file | Required | Optional |
|---|---|---|---|---|---|
| `place` | `pl` | `places/` | `place.md` | `name`, `kind` | `address`, `tags`, `links` |
| `thing` | `th` | `things/` | `thing.md` | `name`, `kind` | `tags`, `links` |

Both are entities: they can be edge endpoints and `context` targets, and can
be named by `entity:` on a note or interaction. They are not person-like:
they have no aliases, cadence, touchpoints, or person-shaped context view.
Both are roster-visible and use `no_ai = "full"`; `no_ai: notes` is not
available for them.

### `place`

A location worth referring to again: a home, workplace, recurring venue,
neighborhood, or city. `kind` is required and suggests `home`, `work`,
`venue`, `neighborhood`, `city`, or `other`. `address` is free text; it is
never geocoded or parsed. Coordinates and structured postal fields are out
of scope; use `links` or the body.

### `thing`

A project, object, work, idea, vehicle, book, or tool worth referring to
again. `kind` is required and suggests `project`, `object`, `work`, `idea`,
`vehicle`, `book`, `tool`, or `other`. A company is an `org`, not a thing;
a one-off event is an `interaction` or a note.

### `kind`

`kind` is one primary noun per record, not a free-form tag soup. It is a
required `non-empty-string`; the vocabulary above is documented and enforced
by the capture skill, not by a closed grammar. `tags` is the cross-cutting
label (`tags: [house-history, renovation]`).

### When a thing is a note

Use a note instead when the fact is dated, sensitive, or owned by exactly one
person/place and never referenced elsewhere. A note carries its own date and
`no-ai`, so it does not bypass note-level privacy. There is no `notes:` or
`serial:` field; standing prose goes in the body, and one-off identifiers go
in the body or a note.

## Fields

This pack owns optional flat front-matter fields on `person` records and the
declared fields on its `place`/`thing` records (spec §8). A value that does
not match its grammar is `E_FRONTMATTER`.

| Field | Grammar | Meaning |
|---|---|---|
| `title` | non-empty string | Job title. |
| `company` | non-empty string | Employer. |
| `location` | non-empty string | Free text; not geocoded. |
| `emails` | list | Contact emails. No syntax validation or normalization. |
| `phones` | list | Contact phone numbers. No parsing or normalization. |
| `links` | labeled list | `LABEL:VALUE` profiles (for example `linkedin:https://…`). |
| `tags` | list | Free-form labels; `/` expresses hierarchy. |
| `birthday` | `YYYY-MM-DD` or `--MM-DD` | Date of birth. |
| `dates` | comma-separated `LABEL:DATE` | Other recurring dates. |
| `relationship` | non-empty string | How the person relates to the operator. |
| `cadence` | `<N>d` or `never` | Keep-in-touch interval; `N` is `1..=3650`. |
| `snooze_until` | `YYYY-MM-DD` | One-off snooze date for the cadence nudge. |
| `kind` | non-empty string | Primary noun for a place or thing. |
| `address` | non-empty string | Free-text place address; private context. |

Lists are comma-separated, optionally wrapped in one `[...]`; entries are
trimmed, non-empty, and unique. A labeled-list splits at the first `:`,
`LABEL` matches `[a-zA-Z0-9_-]+`, and the value is trimmed, non-empty and may
contain `:`.

`cadence: never` is a valid value meaning the person is never overdue: the
cadence rule skips them (no warning, not even the "no contact" variant).

`snooze_until` suppresses `W_CADENCE_OVERDUE` while `as_of < snooze_until`
(the person is eligible again on the snooze date; a past date has no effect).
Only the canonical person's own record is read.

## Edge kinds

Core ships `married`, `introduced`, and `colleague`; `personal@0.3` keeps the
0.2 kinds: symmetric `friend`, `family`, `sibling`, `partner`, and directed
`parent` (`a` is the parent of `b`) and `mentor`. It adds four directed kinds:

| Kind | `a` | `b` | Meaning |
|---|---|---|---|
| `visited` | `person` | `place` | Durable "has been to". |
| `lives_at` | `person` | `place` | Residence; `since` / `until`. |
| `owns` | `person` | `thing` | Ownership; `since` / `until`. |
| `located_at` | `thing` | `place` | Physical location; `since` / `until`. |

`visited` is deliberately durable: a second visit is not a second edge, and
the same ordered pair is `E_DUPLICATE_EDGE`. Individual visits are
interactions or notes attached to the place. `located_at` is only for
physical things; a project is not "located" at a place, so use a note or
interaction instead. A symmetric kind must not appear twice for the same
unordered pair (`E_DUPLICATE_EDGE`); a kind no core or enabled pack claims is
`E_UNKNOWN_EDGE_KIND`.

An edge is visible to agents only when its kind's pack is in scope, both
endpoints are cleared, and the edge's own `no-ai` is not `true`. A
`no-ai: true` place or thing hides every edge touching it while the person
stays visible.

## Verbs

### `touch`

```
DATE touch PERSON-ID call|text|email|meet|meal|event|gift|video|other [note:NOTE-ID] [src:PROVENANCE]
```

Records a touchpoint: called, texted, emailed, met, had a meal with, attended
an event with, gave a gift to, had a video call with, or other. The kind is a closed list; a kind
outside it, a missing kind, a misplaced argument or a duplicate `kind:` pair
is `E_TOUCH_MALFORMED` (a core code). The core mirrored shape is accepted too:

```
DATE touch PERSON-ID [kind:KIND]
```

`note:NOTE-ID` links a note that belongs to the touched person (after merge
canonicalization): an invalid note ID is `E_INVALID_ID`; a `note:` that is not
a note record is `E_WRONG_ID_TYPE`; a missing note, or one belonging to
another person, is `E_UNKNOWN_RECORD`. `src:PROVENANCE` records provenance;
duplicate `src:` values are `E_DUPLICATE_SRC` (core).

## Rules

Both rules are warning-level nudges: they surface what to do next and never
block a write or a commit (#183). Each is configurable
through `[checks]`.

### `W_CADENCE_OVERDUE`

Default severity `warning`; key `personal.cadence_overdue`
(`"warning" | "error" | "off"`).

Fires for a person with `cadence: <N>d` who has no touchpoint on or after
`as_of - N` days (inclusive) and on or before `as_of`. A touchpoint is a
`touch` or `session` ledger line for that person, after merge
canonicalization. `cadence: never` and an active `snooze_until`
skip the person. `as_of` comes from `--as-of`, else `[checks].as_of`, else
today's UTC date.

### `W_DATE_UPCOMING`

Default severity `warning`; key `personal.date_upcoming`
(`"warning" | "error" | "off"`); window `personal.date_upcoming_days`
(default `7`, cap `3650`).

Fires when a person's `birthday` or an entry in `dates` has its next
occurrence within `0..=personal.date_upcoming_days` days of `as_of`. A
year-less `--MM-DD` value is the next `MM-DD` on or after `as_of`.

## Privacy and scoping

The pack honours `no-ai` on person records (`true`, `false`, or `notes`): a
`no-ai: true` person is excluded from `find`, `context`, and agent output,
while a `no-ai: notes` person stays visible but their notes and interactions
default to hidden (spec §13). PII fields (`location`, `emails`, `phones`,
`links`, `tags`, `birthday`, `dates`, `relationship`, and a place's
`address`) are stripped from `context --exclude-private`; `cadence`, `kind`,
and touch metadata stay.

Places and things use `no_ai = "full"` only: `no_ai: true` hides the record
and every edge touching it, while `no_ai: false` keeps it visible. There is
no `no_ai: notes` mode for them. An uncleared place or thing returns no agent
`context` bundle at all, not an empty one, because unlike a person there is no
derived ledger metadata that justifies revealing its existence. The operator
path still returns the bundle with the badge.

Per-pack scoping (#178) applies: `--packs personal@0.3` limits agent reads to
core and personal-owned items in a 0.4 vault; a `personal@0.2` listing is
still a no-op alias and scopes to the active built-in. The `context` view
exposes a non-person-like entity's declared fields in `entity.fields`; the
agent path only sees a cleared record.

Use fake data (`Ada Example`, `Bea Demo`, `Example Studio`, `Example
Bicycle`, fake ULIDs) in tests, fixtures, and examples. Never commit real
contact details.
