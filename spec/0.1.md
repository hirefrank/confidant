# Confidant format spec 0.1

This is the contract for vault files. The CLI version and this spec version
are independent (ADR-1). A vault declares `spec = "0.1"` in `confidant.toml`.
A reader that does not implement this version must fail with `E_SPEC_UNSUPPORTED`
rather than guess.

Milestone 1 covers parsing, generic records, derived values, balance
assertions, `confidant check`, and schema packs. Encryption of
notes and PII is specified here as a layout reservation (`keys/`) and is
implemented in milestone 2 after an independent crypto design review.

## 1. Vault layout

```
vault/
├── confidant.toml
├── confidant.lock              # external pack pins (PD5); plaintext, committed
├── packs/<name>@<version>/     # vendored external packs (PD4); plaintext, committed
├── keys/                      # wrapped per-client data keys (milestone 2)
├── ledger/YYYY/MM.cfd         # dated one-line entries, one file per month
├── people/p-<ULID>/profile.md
├── people/p-<ULID>/notes/n-<ULID>.md
├── orgs/o-<ULID>/org.md
├── deals/d-<ULID>/deal.md
├── interactions/i-<ULID>/interaction.md
├── notes/n-<ULID>/note.md     # notes not stored under a person
└── .confidant/                # local index/cache; gitignored; rebuildable
```

A record may also be a single Markdown file named by its ID
(`people/p-<ULID>.md`). Both forms are valid. IDs appear in paths; names never
do.

`confidant.lock` and `packs/<name>@<version>/` are allowed top-level
entries (external packs, #193). Both are plaintext, committed to git,
and hold no private data: the lockfile pins hashes and sources, the
pack directory holds the pack's manifest, skill text, and contract
file. See `spec/pack-lock.md` and `spec/pack-manifest.md` §13.

Readers skip `.git`, `.confidant`, `keys`, `confidant.toml`, and any **non-symlink**
file or directory whose name starts with `.`, except leftover `.confidant-tmp-*`
files from a crashed atomic write (those are `E_INVALID_FILENAME`). `README.md`
is documentation and is skipped wherever it appears. `LICENSE` is allowed at
the vault root only. A dot-named **symbolic link** is `E_SYMLINK`, never
skipped. Everything else under a collection or record directory is checked or
flagged. A non-conforming filename is `E_INVALID_FILENAME`, never silently
skipped (ADR-3). Unreadable directories and non-UTF-8 names are findings
(`E_UNREADABLE` / `E_INVALID_FILENAME`), not hard errors. Per-entry listing
failures are per-entry findings; a directory that cannot be listed at all is
one `E_UNREADABLE` for that directory and does not invent a missing
`profile.md`.

Symbolic links anywhere under the vault are `E_SYMLINK`, including a
symlinked `profile.md`. Git conflict markers (`<<<<<<<`, `>>>>>>>`) in a vault
file are `E_MERGE_CONFLICT`. When both conflict sides parse as encrypted
envelopes, the finding says the encrypted record has two versions after a
merge conflict and points at `confidant record resolve <id> --show`.
A setext heading underline of `=======` is not a conflict.

## 2. `confidant.toml`

```toml
spec = "0.1"
packs = ["example-pack@0.1"]
vault_id = "01M3TC5H00MPJG005VQC00000B"

[checks]
as_of = "2026-10-08"                          # optional; default is today (UTC)
example-pack.require_duration = "error"      # error | warning | off
example-pack.balance_nonnegative = "error"
example-pack.notes = "warning"
example-pack.gap = "warning"
example-pack.gap_days = 45
example-pack.lookback_days = 180

[inbox]
pubkey = "age1qyqszqgpqyqszqgpqyqszqgpqyqszqgpqyqszqgpqyqszqgpqyqs3290ml"  # optional

[crypto]
mode = "plaintext"  # optional; "encrypted" (default) | "plaintext"
```

- `spec` is required. Only `"0.1"` is defined.
- `vault_id` is required. It is a non-secret opaque identifier bound into
  content encryption in milestone 2. It must be stable for the life of the vault.
- `packs` lists schema packs as `name@version`. Unknown packs are
  `E_PACK_UNKNOWN`. A pack may be compiled into the binary or external
  (vendored under `packs/<name>@<version>/` and pinned in
  `confidant.lock`; see §8 and `spec/pack-lock.md`).
- `[checks]` keys are optional. Severity values are `error`, `warning`, or
  `off` (`warn` and `disable` are not accepted and are `E_CONFIG`). Integer
  keys declared by a pack (for example a gap window in days) are
  non-negative and capped at 3650. Unknown keys, bad types, and negative or
  over-cap day counts are `E_CONFIG`. `as_of` is `YYYY-MM-DD` and is the date
  gap rules use when `--as-of` is not passed. `--as-of` that is not a
  zero-padded calendar date is a usage error (exit 2).
- If `spec` is not `"0.1"`, `check` emits `E_SPEC_UNSUPPORTED` (and any
  `E_CONFIG` findings) and stops. It does not apply 0.1 record or ledger
  rules. External packs are not resolved at all in that case, so a listed
  pack is not also reported as `E_PACK_UNKNOWN`.
- `[inbox]` is optional and backward compatible (readers that do not know it
  ignore it). `pubkey` (optional) is the vault's age X25519 public inbox key
  (`age1…`) that outside tools encrypt intake items to before pushing them to
  the `inbox` git branch. It is published in the vault and is not a secret;
  the private half never lives in the vault. See `docs/inbox.md` and
  `confidant inbox --help`.
- `[crypto]` is optional and backward compatible (readers that do not know it
  ignore it). `mode` (optional) is `"encrypted"` (the default when absent) or
  `"plaintext"`. A plaintext vault keeps every record body unencrypted, so
  anyone with the repository or a clone can read it, history included; the
  mode permits plaintext record writes while the vault is structurally
  plaintext (§14), and it can never downgrade an encrypted vault. Any other
  `mode` value, and any unknown key inside `[crypto]`, is `E_CONFIG`.

## 3. Identifiers

An ID is `prefix '-' ULID`.

The ULID is 26 characters of Crockford base32
(`0123456789ABCDEFGHJKMNPQRSTVWXYZ`), parsed case-insensitively and emitted
uppercase. Non-ASCII characters are rejected. The first character must be
`0`–`7` (the timestamp's high bits). The CLI generates ULIDs; `check` rejects
anything else (`E_INVALID_ID`). The same ULID under two prefixes is
`E_DUPLICATE_ULID`.

| Prefix | Type          | Path stem                          |
|--------|---------------|------------------------------------|
| `p`    | person        | `people/p-<ULID>`                  |
| `o`    | org           | `orgs/o-<ULID>`                    |
| `d`    | deal          | `deals/d-<ULID>`                   |
| `i`    | interaction   | `interactions/i-<ULID>`            |
| `e`    | edge          | `edges/e-<ULID>/edge.md`          |
| `n`    | note          | `notes/n-<ULID>` or `people/…/notes/n-<ULID>.md` |
| `pkg`  | package       | schema packs; ledger only in 0.1   |

The path prefix and the ID prefix must agree (`E_TYPE_PATH_MISMATCH`). The
filename or directory name must equal the front matter `id` (`E_ID_PATH_MISMATCH`).

## 4. Markdown records

Each record is Markdown with YAML-like front matter. Front matter holds
identity and display fields, not facts (ADR-2).

```markdown
---
id: p-01M3TC5H00MPJG000000000000
type: person
name: Ada Example
---
Context, goals, preferences. Prose only.
```

Required keys: `id`, `type`. `type` is `person`, `org`, `deal`, `interaction`,
`note`, or `edge`.

Allowed keys in 0.1:

| Key      | Records                         | Meaning                                      |
|----------|---------------------------------|----------------------------------------------|
| `id`     | all                             | Record ID                                    |
| `type`   | all                             | Record type                                  |
| `name`   | person, org, deal, interaction  | Display name                                 |
| `date`   | note, interaction               | `YYYY-MM-DD`                                 |
| `person` | note, interaction, deal         | Person ID                                    |
| `org`    | note, interaction, deal         | Org ID                                       |
| `deal`   | note, interaction               | Deal ID                                      |
| `session`| note                            | `YYYY-MM-DD` of the session this note covers |
| `a`      | edge                            | Person ID: first endpoint of the relationship |
| `b`      | edge                            | Person ID: second endpoint of the relationship |
| `kind`   | edge                            | Edge kind name (closed list, see below) |
| `since`  | edge                            | `YYYY-MM-DD` the relationship started |
| `until`  | edge                            | `YYYY-MM-DD` the relationship ended |
| `with`   | interaction                     | `[p-…, p-…]` participant list (see below) |
| `no-ai`  | person, note, interaction, deal | `true` / `false`; `notes` is also valid on person records (else `E_FRONTMATTER`). On any other record type, `no-ai` is `E_FRONTMATTER`. See sections 12–13 |

Unknown keys are ignored by 0.1 readers (forward compatible) and are not
facts. ASCII case variants of exactly the three reference keys (`Person:`,
`PERSON:`, `Deal:`, …) count as those keys: their values must be record
IDs under the section 12 rules. Alias or custom keys (`client:`, …) are
never references. Structured facts belong in the ledger. Duplicate keys are
`E_FRONTMATTER`. An `edge` record is the one exception to this tolerance: it
allows only `id`, `type`, `a`, `b`, `kind`, `since`, and `until`, and any
other key is `E_FRONTMATTER` (see the edge rules below). A `person` / `org` /
`deal` value that is not a valid ID is `E_INVALID_ID`; a well-formed ID with
no record is `E_DANGLING_REF`.

Values are unquoted, double-quoted, or single-quoted scalars, except
`with:`, which is a bracketed comma-separated list. Double-quoted
values round-trip escapes for `"` and `\`. Booleans are `true` and `false`.
There is no nested YAML in 0.1. The opening and closing `---` fences may
have trailing ASCII spaces or tabs.

The body is prose. It is never the source of truth for sessions, stages,
balances, or aliases.

An **edge** record is a relationship between two people: `a` and `b` are
person IDs, `kind` names one entry from the closed kind list, and `since`
/ `until` are optional `YYYY-MM-DD` bounds. Core ships `married`
(symmetric), `introduced` (directed), and `colleague` (symmetric); packs
add their own kinds, each declaring `symmetric: bool` (see §8). An edge
carries **no body**: a body on an edge is `E_FRONTMATTER`. Its front matter
is closed too: only `id`, `type`, `a`, `b`, `kind`, `since`, and `until` are
allowed, and any other key is `E_FRONTMATTER`. Sensitive context belongs in
a note on one of the edge's people, which does get crypto-shredded; an edge
body — or any other value carried on the edge — would survive shred as
shared-key residue.
`no-ai` is not allowed on edges. `check` rules for edges: both ends must
exist (`E_DANGLING_REF`), the ends must be person records
(`E_WRONG_ID_TYPE`), `a` must not equal `b` (`E_SELF_EDGE`), `kind` must
be known (`E_UNKNOWN_EDGE_KIND`), and a symmetric kind must not appear
twice for the same unordered pair (`E_DUPLICATE_EDGE`). A missing `a`,
`b`, or `kind` is `E_FRONTMATTER`. A malformed end is `E_INVALID_ID`.

An **interaction** with several participants is one record, routed and
encrypted to the primary's key, with `with:` listing the other
participants as a front-matter bracketed list of plain person IDs:
`with: [p-…, p-…]`. `with:` is metadata only: it does not change routing
or encryption. `check` rules for `with:`: each entry must be a valid `p-`
ID, must not be the primary itself, and must not repeat. Checking that
each entry *exists* is a **keyed check**: `with:` lives inside the
ciphertext, so it runs only when `check` can read the record's plaintext.
Cleaning a `with:` list up on shred is deferred (see §14).

### Editing a record

A record's file may be replaced in place (`confidant record edit`), which
keeps one file per record and one commit per change. An edit carries the
same rules as any other write:

- The input must be a complete record, and its `id:` must equal the record
  being edited. The target path is derived from that id, never from the path
  the caller passes, so a wrong file cannot clobber another record.
- The write is `check`-gated and makes one commit per edit. A rejected edit
  leaves the file untouched.
- An edit writes the record's **canonical form** (§4), the same
  serialization `record add` uses. A record stored in a non-canonical
  layout is normalized by its first edit, so front-matter comments and
  non-canonical quoting do not survive one.
- An edit whose content is byte-identical **and** whose derived outer
  `no-ai` header is unchanged is a **no-op**: nothing is written and nothing
  is committed, and in an encrypted vault the stored ciphertext is reused as
  it is, so the record keeps the key epoch it was written under. When the
  derived header has moved — because a person the record references changed
  mode — the record is re-encrypted instead, which is what refreshes it.
- In an encrypted vault an edit that must write re-encrypts under the
  current epoch for the record's current client, with a fresh nonce and the
  same AAD bindings (§14), and stamps `no-ai` from the new content (§13).
  Editing a `deal` so its `person:` changes moves the record to that
  person's key; if the previous key is unavailable on this device the edit
  fails closed rather than rewriting a record it cannot read.
- The replaced ciphertext leaves the working tree but stays in git
  history: the pre-edit version remains readable with the key epoch that
  wrote it, for as long as that epoch's key exists — for a client's
  records, until that client is shredded (§14).
- In an encrypted vault, editing a **person** whose effective `no-ai` mode
  changes (§13) re-stamps that person's existing children in the same
  commit. Every record whose front matter references the person — the same
  reference set the write-time stamp uses — has its outer header
  re-derived; records whose header actually changed are re-encrypted under
  the current epoch, and unchanged records keep their ciphertext
  byte-for-byte. The edit's `--json` `files` names only the records
  actually rewritten, so it matches the commit diff. The edit refuses,
  with nothing committed, when any record cannot be read to determine
  whether it references the person; the refusal names those files so they
  can be fixed or shredded first. A child whose header no longer hides
  (the person loosened) is re-stamped the same way, so it decrypts
  normally again. This re-stamp looks forward only: a header that went
  stale before it existed is corrected the next time the person's mode
  changes or the child record is re-saved, not retroactively.
- An edit adds no finding code: §9 and §10 are unchanged.
- Notes are not edited by this verb in 0.1.

## 5. Ledger grammar

Facts are one-line entries in `ledger/YYYY/MM.cfd`. The filename month must
match every entry date (`E_LEDGER_DATE`). The path must be exactly
`ledger/YYYY/MM.cfd` with a two-digit month (`E_LEDGER_PATH`).

```
line       = blank | comment-line | entry
comment-line = *WS ";" *ANY
entry      = date 1*WS verb 1*WS id *(1*WS arg) [comment]
comment    = *WS ";" *ANY
date       = 4DIGIT "-" 2DIGIT "-" 2DIGIT   ; zero-padded, valid calendar date
verb       = 1*LOWER *(LOWER / DIGIT / "-")
id         = prefix "-" ulid
arg        = quoted / pair / token
pair       = key ":" (quoted / unquoted-value)
quoted     = DQUOTE *(unescaped / escaped) DQUOTE
token      = 1*(VCHAR except space, semicolon, DQUOTE)
```

A leading UTF-8 BOM is stripped. Dates are strictly `YYYY-MM-DD` (zero-padded)
and must be followed by whitespace. Blank lines and whole-line comments are
ignored. Trailing comments start at `;` and are not part of the arguments.
Verbs are canonicalized to lowercase. Pair values may be quoted so they can
contain `:`, whitespace, `;`, or `"`. Unquoted pair values still cannot
contain whitespace. A parser must round-trip Unicode in quoted strings.

Example:

```
; ledger/2026/10.cfd
2026-10-01 touch    p-01M3TC5H00MPJG000000000000 call
2026-10-03 alias    p-01M3TC5H00MPJG000000000000 email hmac:6f2c9a1d8b7e4f301122334455667788
2026-10-08 touch    p-01M3TC5H00MPJG000000000000 meet note:n-01M3TC5H00MPJG002NAM000005
2026-10-08 balance  p-01M3TC5H00MPJG000000000000 unknown_metric 4
2026-10-09 stage    d-01M3TC5H00MPJG00248G000004 proposal
2026-10-12 merge    p-01M3TC5H00MPJG001248000002 into p-01M3TC5H00MPJG000000000000
```

A parser must round-trip semantically: `parse(format(entry)) == parse(original)`
for every valid entry, ignoring whitespace between tokens.

## 6. Core verbs

These verbs exist without a pack.

### `alias`

```
DATE alias ID KIND hmac:HEX
```

`KIND` is `email`, `phone`, `handle`, or `name` (#748: `name` covers a former/married name, nickname, or preferred name; it is an alias only and never renames the record). The line is exactly those two
arguments: `KIND` plus `hmac:HEX`. The value is a keyed HMAC, never plaintext
PII (ADR-2, ADR-9). `HEX` is at least 32 hexadecimal characters.
Anything else is `E_ALIAS_PLAINTEXT`. Two canonical IDs sharing the same
`(kind, hmac)` is `E_ALIAS_COLLISION` (warning).

Lookup path: a `name` alias is found only through `alias resolve name`.
Plain `resolve` matches the record's display name and `find` scans
plaintext, so neither consults alias lines — a former name that appears
nowhere else in plaintext will not surface through them. The two lookup
paths are independent and neither takes precedence over the other, so they
can disagree: if person B's display name equals person A's `name` alias
value, `resolve` returns B while `alias resolve name` returns A, and `check`
reports no collision for it — alias values are HMAC-only and the check
engine holds no key with which to compare a `name` alias against a display
name.

The HMAC covers the alias value normalized as: NFC, then trim surrounding
whitespace, then Unicode lowercase. Importers must apply the same rule
before hashing: the same alias in precomposed (NFC) vs decomposed (NFD)
form must hash identically, or an importer matching on one form will miss
records written with the other.

### `merge`

```
DATE merge FROM into TO
```

Folds `FROM` into `TO`. The old ID stays resolvable; its history is kept.
`FROM` and `TO` must exist (`E_UNRESOLVED_MERGE`). An invalid `TO` token is
`E_INVALID_ID`. `FROM` and `TO` must have the same ID prefix; a merge
between different record types (for example `merge p-X into o-Y`) is
`E_WRONG_ID_TYPE` and is not applied. `FROM` must not equal `TO`
(`E_SELF_MERGE`). Cycles are `E_MERGE_CYCLE`. The same `FROM` merged into
two different `TO`s is `E_MERGE_FORK` (first wins). A merge takes effect
from its own date: when evaluating a `balance` assertion dated `D`, apply
only merges dated on or before `D`. Later merges never change earlier
assertions. Current-state views, alias lookups, and gap rules evaluated at
`as_of` apply merges dated on or before `as_of`. Once the evaluation date
is on or after the merge date, `FROM`'s whole history, including events
before the merge, counts toward the canonical ID.

### `stage`

```
DATE stage DEAL-ID TOKEN
```

Records a deal stage change. `TOKEN` is a free-form stage name (`proposal`,
`won`, `lost`, …). The ID must be a deal (`E_WRONG_ID_TYPE` otherwise) and
must exist.

### `balance`

```
DATE balance ID METRIC NUMBER
```

An assertion, not a fact. `check` computes `METRIC` from the ledger **as of
the end of the assertion's date**: every entry dated on or before that day
is included; later entries never affect it. A mismatch is the owning
pack's code (for example a pack's balance-mismatch code). Core does not
define metrics; packs do. Metrics no
enabled pack defines are `E_UNKNOWN_METRIC`, unless they belong to a
registered pack that is not enabled (then they are `W_PACK_ORPHAN`,
see §8).

### `touch`

```
DATE touch P-ID [kind:KIND]
DATE touch P-ID call|text|email|meet|meal|event|gift|video|other [note:NOTE-ID] [src:PROVENANCE]
```

A lightweight or mirrored touchpoint on `DATE` for `P-ID`. In core, `record
add` writes a minimal mirrored `DATE touch P-ID [kind:KIND]` line for an
interaction's primary `person:` and one per `with:` participant when an
interaction is added, so a logged interaction counts as contact for everyone
on it (a dateless interaction mirrors nothing). The built-in personal pack is
implicit (see `packs/personal/0.2.md` and §8), so `touch` always accepts a
positional kind from the closed list (`call`, `text`, `email`, `meet`,
`meal`, `event`, `gift`, `video`, `other`) plus optional `note:NOTE-ID` and
`src:PROVENANCE` pairs (written by `confidant log touch`). Any other argument
shape is `E_TOUCH_MALFORMED`. `context` shows a person only their own
touchpoints. `touch` is a core verb; the personal pack claims it and owns
touch lines.

Semantic idempotency (#747): two `touch` lines are the same touchpoint
when they share the person, the date, and the kind; `note:` and `src:`
pairs do not distinguish them. `confidant log touch` refuses to write a
touchpoint that already exists (exit 1, `E_ALREADY_EXISTS`) unless
`--force` is passed for a genuinely separate contact the same day, and
the same rule covers `log session` (same person, date, duration, and
billing tag; `60m` and `1h` are the same duration, and tags compare
lowercased). The billing tag is a closed vocabulary; `log session` rejects any
other tag, including a correctly spelled tag in the wrong case. The
vocabulary is the union of the enabled packs' `session-checks`
`billing_tags` for verb `session`, falling back to (`paid`, `pps`,
`comp`) when no enabled pack declares any — so a pack that bills
under different tags is not overruled at log time, while tag
enforcement itself stays fail-closed: an unlisted tag still fails.
The MCP `log_touch` and `log_session`
tools expose the same `--force` escape hatch. A retry carrying a
`--request-id` the vault already knows is decided by request-id
idempotency (an exact retry replays, a reused id with different content
conflicts) instead of by this refusal. Lines already queued to the
inbox are invisible to the write-time refusal (they are encrypted to
the inbox key), so the inbox drain skips a queued line whose identity
already exists in the ledger or was already merged in the same drain
run — and the drain report names the drop: each item reports how many
of its lines were dropped as semantic duplicates, distinct from
`src:`/exact-text re-import skips. A forced repeat is not dropped:
a line queued by `log --force --fallback-inbox` carries a `force: true`
header on its inbox item and drains to a real ledger line, and
`confidant inbox --force` processes unmarked duplicates the same way
(a rotate drain never forces). `check` flags every repeat `touch` line after the first as
`W_DUPLICATE_TOUCH`, except kind-less mirrored lines, which carry no
identity and are never flagged; it flags every repeat `session` line
after the first as `W_DUPLICATE_SESSION`. Both are warnings, so they
never block writes under the default fail-on-error behaviour — but a
vault with historical duplicates that runs `check --fail-on warning`
will now fail where it previously passed. `context`
does not collapse duplicates: it shows every ledger touchpoint line, so
its counts are line counts, not distinct contacts — the ledger keeps the
full history and the duplicates stay visible until removed (see #746).

A ledger ID that is well-formed but has no record file is `E_UNKNOWN_RECORD`.
`stage` / `open` / `session` on the wrong record type is `E_WRONG_ID_TYPE`.
A merge between different record types is `E_WRONG_ID_TYPE`.
A verb that is neither core nor in an enabled pack is `E_UNKNOWN_VERB`,
unless it belongs to a registered pack that is not enabled (then it is
`W_PACK_ORPHAN`, see §8).
Duplicate `src:` provenance is `E_DUPLICATE_SRC`.

## 7. Derived values

Derived values are computed, never stored as truth (ADR-2). Packs register
metrics; the built-in personal pack registers none in 0.1.

Corrections are new entries (or a later `balance` that will fail until the
ledger is right). Do not edit history in place.

## 8. Schema packs

A pack declares extra verbs, extra metrics, and extra check rules. The
built-in personal pack is compiled into the binary behind this interface;
external packs are vendored into the vault, and the on-disk
pack documents in `packs/` are the human-readable contracts.

The **personal pack is implicit**: it is enabled in every vault, whether or
not the vault lists it, so `packs = []` still enables it. A `personal@…`
entry in `packs` is accepted as a no-op (it never turns the pack off, and it
never makes the pack known at a specific version). An external pack is
opt-in: a vault that lists it enables it, and removing it turns
its verbs, fields, and metrics into `W_PACK_ORPHAN` warnings (see below)
instead of errors. The personal pack's data is never orphaned.

### Multi-pack loading (#177)

One vault can enable several packs at once. Each ledger verb, record type,
front-matter field, and balance metric belongs to exactly one pack (or to
core). Ownership is decided by verb, field, type, and metric name — ledger
lines carry no pack tag.

- **Registry.** The binary holds a static registry of compiled packs plus the
  implicit built-in packs. `check` resolves the vault's `packs = [...]` list
  against it; a listed pack no pack implements is `E_PACK_UNKNOWN`, except a
  built-in listed at any `name@…`, which is a no-op. A duplicated listing
  folds once.
- **Built-ins are not installed.** A built-in ships inside the binary. A vault
  may not vendor it or pin it: any `packs/<built-in>@…/` directory or
  `confidant.lock` entry for a built-in name fails closed as
  `E_PACK_INVALID`, listed or not.
- **Conflicts.** Two enabled packs claiming the same verb, record type,
  field, balance metric, or edge kind is `E_PACK_CONFLICT`. `check` reports the
  conflict and skips all pack folding (core checks still run); the operator
  removes one of the packs or resolves the overlap.
- **Fields.** Pack-specific fields on a shared record (e.g. a `birthday`
  field on a `person` record) use flat names plus an ownership registry.
  Namespacing (`personal.birthday`) applies only when two packs actually
  collide — and a collision is `E_PACK_CONFLICT`, so namespaced fields do
  not occur in practice.
- **Disabled packs.** Data owned by a registered pack that is not enabled
  is `W_PACK_ORPHAN` (warning, never error): orphaned verbs, fields, record
  types, and balance metrics warn instead of erroring. Warnings never block
  writes, matching the #183 rule.
- **Edge kinds.** A pack may declare edge kinds, each `{ name, symmetric }`.
  The kind's owning pack decides edge visibility: an edge is visible
  exactly when its kind's pack is in scope. An edge whose kind belongs to
  a registered pack that is not enabled warns `W_PACK_ORPHAN` instead of
  erroring. An edge whose kind has no owner at all is visible only
  unscoped (fail-closed) and is `E_UNKNOWN_EDGE_KIND`. The edge's own
  front matter has no pack-owned fields to filter.
- **Calculations.** Each enabled pack folds the ledger independently and
  emits its own findings. `context` output groups pack state by pack in
  the `packs` map. The legacy top-level `coaching` field duplicates the
  entry of a pack named `coaching` for contract stability (ADR-7).

See [spec/pack-manifest.md](pack-manifest.md) for the pack contract format.

### Pack versioning (#190)

A vault pins each pack at an exact `name@version`. A binary supports a
*range* per pack (e.g. `example-pack` 0.1–0.2). The rules, in order of
increasing consequence:

- **Minor / compatible bump** (`0.1` → `0.2`, same schema): the binary
  reads lines and fields written under the older version as-is, and
  `doctor` warns that a newer pack version is available.
- **Breaking bump**: a `confidant migrate pack <name>@<ver>` command
  rewrites the affected lines/fields in one commit, runs `check` under the
  new version, and updates the pin. It is dry-run by default. (The
  `migrate` command is not built yet — reserved until a pack actually
  ships a breaking 0.2, likely alongside the external-pack loader #193.)
- **Binary too old**: a binary that does not support the pinned version
  refuses writes with `E_PACK_VERSION` (reserved) and a clear "upgrade
  confidant" fix, rather than falling back to `E_PACK_UNKNOWN`.

### External packs (#193)

An external pack is vendored into the vault at
`<vault>/packs/<name>@<version>/` and pinned in `<vault>/confidant.lock`
(`spec/pack-lock.md`). Its manifest is v2 (`spec/pack-manifest.md`
§13); its rule kinds are implemented in core Rust.

- **Resolution order.** For each `name@version` in `confidant.toml`,
  `check` looks first for a compiled pack, then for a lockfile entry
  with a matching vendored directory. A compiled pack always wins on
  the same `name@version`; any lockfile entry for it is ignored
  (`doctor` notes it).
- **Hash verification.** The vendored directory's canonical tree digest
  must match the lockfile `hash` (`spec/pack-lock.md` §3). Mismatch or
  a missing directory is `E_PACK_HASH`.
- **Validation.** Manifest and contents are validated at load (name
  regex, reserved names, capability limits, file allowlist;
  `spec/pack-manifest.md` §13.3–§13.5). Failure is `E_PACK_INVALID`.
- **Fail closed.** A pack that is missing from the lockfile, missing on
  disk, fails hash verification, or fails validation produces an error
  finding and is not folded (PD12). Because writes are `check`-gated,
  writes are blocked until it is fixed.
- **No network at `check` time.** `check` and `doctor` never fetch;
  only `confidant pack add|update` touch the network (PD9).
- **Scope.** External packs affect `check` only (PD16): findings from
  `[[fields]]` grammars, declared rule kinds, and message templates —
  except that a pack declaring `[context]` also affects `context`,
  strictly scoped to derived ledger metadata (`spec/pack-manifest.md`
  §13.9). `context_view` returns `None` for external packs except for the
  view `[context]` names; `private_context_fields` is always empty for
  them.

## 9. `confidant check`

`check` is read-only. It collects every finding and does not repair (the
collect-don't-throw rule). It runs on every write in later milestones; in
milestone 1 it is the product.

Default `--fail-on error`. `--fail-on warning` also fails on warnings.
`--json` prints the report below. `--as-of YYYY-MM-DD` overrides `[checks].as_of`
(a malformed `--as-of` is a usage error, exit 2).

Human output names opaque ID paths, never display names, so it leaks nothing
beyond the vault's own IDs.

### JSON report

Every JSON response includes the resolved vault path (ADR-7, ADR-11).

`schema_version` is `"1"` for this JSON object shape (independent of vault
`spec`). `--json` command failures use the same field and are written to
**stdout**, including the resolved `vault` path when discovery succeeded.

```json
{
  "schema_version": "1",
  "ok": true,
  "vault": "/absolute/path/to/vault",
  "spec": "0.1",
  "summary": {
    "records": 12,
    "ledger_entries": 8,
    "errors": 0,
    "warnings": 0
  },
  "findings": []
}
```

A finding:

```json
{
  "code": "E_UNKNOWN_METRIC",
  "severity": "error",
  "file": "ledger/2026/10.cfd",
  "line": 5,
  "id": "p-01M3TC5H00MPJG000000000000",
  "message": "unknown metric",
  "fix": "Use a metric an enabled pack defines, or remove the balance line"
}
```

`file`, `line`, `id`, and `fix` are omitted when they do not apply. Findings
are sorted by severity (errors first), then `code`, `file`, `line`, `message`.
Callers classify by `code`, never by message text.

Command failures (no vault, usage) use a different envelope:

```json
{
  "schema_version": "1",
  "ok": false,
  "vault": null,
  "error": {
    "code": "E_VAULT_NOT_FOUND",
    "message": "no vault found",
    "fix": "Pass --vault, set CONFIDANT_VAULT, or run from a vault directory"
  }
}
```

Usage errors exit 2. Other command failures exit 1. `internal_error` is
reserved for unclassified failures. A completed `check` that finds problems
exits 1 (or 0 if they are below `--fail-on`) and uses the report envelope, not
the error envelope.

## 10. Stable finding codes

Codes are part of the spec. Do not reuse a code for a different meaning.
See [findings.md](findings.md).

## 11. Vault discovery (ADR-11)

Resolve in this order:

1. `--vault <path>`
2. `CONFIDANT_VAULT` (a path, or a name listed under `[vaults]` in the user config)
3. Walk up from the current directory looking for `confidant.toml`
4. `default_vault` in `~/.config/confidant/config.toml`

If nothing is found, fail with `E_VAULT_NOT_FOUND`. Never fall back silently
to an implicit home-directory vault that was not declared.

## 12. Search (milestone 1)

`confidant find QUERY` decrypts nothing (files are plaintext until milestone 2)
and scans original record files and original ledger lines (including
unparsable lines). Matching is Unicode case-insensitive (practical case
folding, including `ß` → `ss`). `line` is the 1-based line number in the
file. Each hit returns `id`, `path`, `line`, and `excerpt`.

`find` is an allowlist. It computes a **cleared** set as a fixed point and
returns content only from cleared records and ledger lines. A record is
cleared only when all of these hold:

- it parsed cleanly;
- it has no `E_DUPLICATE_ID` or `E_ID_PATH_MISMATCH` on that record.
  `E_ID_PATH_MISMATCH` on a note, interaction, or deal uncleares only
  that record (a misfiled note under `people/<id>/notes/` does not hide
  the person's profile or other notes). `E_ID_PATH_MISMATCH` or
  `E_DUPLICATE_ID` on a person's profile uncleares that whole person;
- it has no `no-ai: true` flag (a `no-ai: notes` person record stays
  cleared — the mode hides their notes, not the person — while a note or
  interaction with no explicit `no-ai` of its own whose person or
  merge-group peer has `no-ai: notes` is uncleared; an explicit
  `no-ai: false` on the child still overrides);
- every ID-shaped token in its raw front matter — keys, values, and `#`
  comments — is a cleared record (case-insensitive scan; this covers
  `person:`, `deal:`, `[[p-…]]`, junk around IDs, and IDs hiding in
  comments or as keys);
- it has no malformed ID token in front matter;
- every member of its merge group is cleared (undirected, every merge date;
  a leading Markdown bullet `*`, `-`, or `+` plus whitespace is skipped
  before detecting a `merge` or `open` verb);
- for anything under `people/<id>/`, that person is cleared;
- for a note, interaction, or deal, every ledger line that names it is
  allowed (every ID-shaped token on that line is cleared; parsed or not,
  including uppercase, `[[n-…]]`, quoted, unparsable, `src:i-…`, a deal
  on a stage line, and mis-named `*.cfd` lines). This rule does not
  apply to persons;

Dangling or unknown IDs are not cleared, so a reference to a missing
profile excludes the record. A `pkg-` ID is cleared only if every person
who opened it is cleared; a `pkg-` ID that no `open` line mentions is
uncleared. A ledger line, parsed or not, is searchable only if every
ID-shaped token in it is cleared. A token counts as a malformed ID if it has a record prefix, an ASCII or
Unicode dash (Unicode Dash_Punctuation plus U+30FC and U+2043; U+00AD and
U+2212 also count), and either an alphanumeric run 20–32 characters long that
fails ULID validation, or a run longer than 32 whose first 26 characters
canonicalize to a ULID (word boundary). A run of dashes after a prefix
(`--`, U+00AD then `-`, two Unicode dashes) is treated as a single dash;
followed by a ULID or near-ULID it is Malformed with that candidate
(`p--<ULID>`, `p­-<ULID>`). These dash rules apply everywhere the scanner
runs: body lines, ledger lines, and non-ref front-matter keys. A prefix is **glued** after an
ASCII alphanumeric or `_`, when the `-` before it follows an alphanumeric,
`_`, or `-` in the same run (`Ana-p-<ULID>`), or when it sits inside a
`scheme://` token. In a glued context: prefix + a single ASCII `-` + an exact ULID
is Valid (`xp-<ULID>`, a hidden person's ID inside a URL); if the run is
longer than 26 and the first 26 characters form a valid ULID, the token
is Malformed with that candidate (`https://example.com/p-<ULID>abc`,
`Ana-p-<ULID>s`); a Unicode dash or a dash run after a glued prefix followed by a
valid ULID is Malformed with that candidate (`Ana-p–<ULID>`). Otherwise
a glued prefix is not a token, so Notion URLs, `Kickoff-session-<token>`,
and Google Docs/Drive IDs (`1g1G7TFxyqPTV83aBwi_-n-…`,
`1b3Yf11-n-m7v…`) stay searchable. A run of exactly 32
lowercase hex characters is never an ID (`Phase-I-<32hex>`,
`My-Page-p-<32hex>`). After `_` the prefix is glued, so the glued rules
apply (`_p-<ULID>` is Valid; `_p-<Drive-id>` is not a token). A bare
26-character Crockford ULID that exactly equals any ULID the vault names is
treated as that ID, including as any 26-character window inside a longer
Crockford run (case-insensitive; `src:zoom/rec_<ULID>.vtt`, `p_<ULID>`,
`p<ULID>`, `<ULID>abc`, `t-<ULID>`), but not a window already covered by a
prefixed token on that line (a record's own `id:` line is not a bare
window). Named ULIDs come from prefixed Valid or Malformed-candidate tokens
anywhere (record bodies, front matter including comments and keys, ledger
lines, `pkg-` IDs, dangling IDs) and from every visited file or directory
name, including nested directories, unknown top-level directories, skipped
dot-names, multi-extension names, `(copy)` suffixes, and uppercase prefixes
(`n-<ULID>.md.bak`, `n-<ULID> (copy).md`, `N-<ULID>.md`, `<ULID>.md`,
`.n-<ULID>.md.swp`, `notes/sub/…`). A name that is exactly a loaded
record's id (`p-<ULID>`, `n-<ULID>.md`) does not add an extra uncleared
ULID. Each mapped ID stays uncleared unless it is a cleared record or a
cleared package. ULIDs seeded *only* from a dangling or malformed prefixed
token (not a loaded record and not a path/file/directory name) match
genuinely bare windows only; they do not un-clear a loaded record via a
prefixed token, including its `id:` line. Loaded records and path-derived
IDs still apply inside prefixed tokens: a Valid token fails if any loaded
or path-named ID with that ULID is uncleared. Exact vault match only; there
is no malformed or near-ULID rule and no 32-hex exemption on this path. It
uncleares a record in front matter, drops a body or ledger line, and links
`merge` / `open` the same way a prefixed ID would. Dropping a record from
the allowlist is a worklist to a fixed point: merge peers of every dropped
id (including a package dropped because an opener was dropped) are dropped,
and every dropped record requeues its dependents. A U+00AD directly after an ID prefix
is treated as `-` before other format characters are stripped. Shorter lookalikes
(`I-95`, `D-Day`, `P-value`, `O-1`, `I-9`, `I-140`, `N-400`,
`Lin I-Chen`, `I—I`) are not IDs. Invisible characters with the Unicode
Default_Ignorable_Code_Point property (Cf — ZWSP, soft hyphen, word
joiner, BOM, bidi marks, tags — plus variation selectors, the grapheme
joiner, Hangul/Khmer fillers, and the whole ranges 2060–206F,
FFF0–FFFB, E0000–E0FFF (which include unassigned ignorables)) are
stripped before scanning, so they
cannot split or hide an ID. Line and paragraph separators are not
stripped: they still break runs. A malformed token carries an
embedded candidate ID when a Unicode-dash run canonicalizes, a dash run
plus ULID canonicalizes, or the first 26 characters of a longer run do. A malformed token in a body line drops
that line only; it never hides the whole record. A malformed token in
front matter makes the record uncleared and is `E_INVALID_ID` (line
number; key name only when it is a known spec key; never the token). A
leading U+FEFF is stripped before fence layout so body-line filtering
uses the same offsets as parse. A `person:`, `org:`, or `deal:` value —
including ASCII case variants (`Person:`, `ORG:`, …) — that
does not parse as a record ID (after stripping invisible characters, quotes,
a trailing comment introduced by one or more spaces or tabs then `#`, including
after a closing quote (`"p-…" # Ada`, `"p-…"  # Bea`, `"p-…" \t# Bea`,
`'[[p-…|Ada]]' # c`), and
`[[id|Alias]]` only inside `[[…]]`) makes the record uncleared
and is `E_INVALID_ID`. A bare `p-A|Name` is `E_INVALID_ID`. Empty, `~`,
and YAML `null` are not references. Repeat
until nothing changes. Name-only mentions with no ID are not detected in
body prose and comments; they *are* detected on `person` / `org` / `deal`
keys (including case variants — `Person: Ada Example` is `E_INVALID_ID`),
but never on alias or custom keys (`client:` stays ignored).
Case-duplicate keys are ambiguous: when both `person:` and `Person:`
appear, the first in key sort order wins for the record's person, and
both are validated.
Every regular, non-hidden file under `ledger/` is read for note links,
merges, and package openers, whatever its name or extension (`09.CFD`,
`.orig`, `~`, `.bak`). `E_LEDGER_PATH` still fires when the path is not
`YYYY/MM.cfd` (case-insensitive `.cfd`); those files are never searched.
In-vault symlinks (files and year directories) are resolved only when the
target stays inside the vault; otherwise the ledger is unreadable. If any
ledger file cannot be read, `find` refuses with command error
`E_LEDGER_UNREADABLE` (code and count only, no path, no hits). `check`
still reports `E_UNREADABLE`.

Remaining limits: a glued prefix whose run is not an exact ULID and whose
first 26 characters do not canonicalize is not a token; alias or custom
keys holding names (`client:`, …) are not treated as `person` / `org` /
`deal`; invisible characters inside a key name are not stripped, so
`Per<U+FE0F>son:` stays ignored — the same alias/custom-key limit;
name-only prose is
not detected. Bare ULIDs that match no ULID the vault names are ignored.
`check` messages never echo user-chosen filenames or directory names;
the structured `file` location field still shows the path of an invalid
file so the operator can fix it.

Any front-matter key that, after stripping surrounding quotes, then
case-folding and removing every non-alphanumeric character, equals
`noai` other than the exact key `no-ai` (quoted or not) is
`E_FRONTMATTER`, and the record is uncleared. `"no-ai"` and `'no-ai'`
are the real flag.

A `find` finding is kept verbatim only when it has no file and no ID
(config-level), or when it resolves to a cleared record or a cleared
ledger line. Everything else is reduced to its code and the count of
affected items. It never includes a path, file name, ID, key, or line
text.

`check` never echoes a raw front-matter value. It names the key only when
that key is a known spec key; otherwise it gives the line number only.
Ledger parse errors give the line number and code without echoing tokens.
Check messages never interpolate free text from the vault (verbs, `src:`
values, raw numbers, unknown metric names, user-chosen filenames or
directory names); they keep the line number, code, and an expected type
where it helps (`expected integer`). The `file` location field still
shows the path of an invalid file. `E_CONFIG` may echo an unknown
`[checks]` key.

If `spec` is not `0.1`, `find` fails with command error `E_SPEC_UNSUPPORTED`
and does not scan. If any ledger file is unreadable, `find` fails with
`E_LEDGER_UNREADABLE` and does not scan. Load findings (partial vault) are
included in `find --json` as `findings`. This is a stopgap; QMD search
comes after v0 (section 9b).

A `find` search that returns zero matches while `skipped_encrypted > 0`
adds a `W_SKIPPED_ENCRYPTED` warning finding (in `findings` in JSON, in
the findings block in text, plus a stderr note in text mode; the TUI
Search view renders it in its status block): encrypted records were not
searched, so the zero result does not establish absence. Exit status is
unchanged (still success), and the `skipped_encrypted` count is still
reported alongside it. Under a `--packs` scope the warning still fires
on the vault-wide skip count — a skipped record's pack ownership is
unknowable without decrypting it — and the message says the count is
vault-wide. The warning is deliberately empty-only for #718: a non-empty
result over skipped records is still partial (the count reports the
skips), and extending the warning to partial results is follow-up work,
not part of this fix. An empty query runs no search and carries no
warning. A refused-only zero match (tampered envelopes, no skips)
carries no `W_SKIPPED_ENCRYPTED` either; see `spec/findings.md` for why
refused envelopes are excluded.

When `qmd` is on PATH and `<vault>/.confidant/qmd-corpus/` exists,
`find --json` adds an optional top-level `hint` string naming the
ranked-search alternative (e.g. the `qmd-search` skill); text output
prints the same line on stderr. The field is absent otherwise. It never
changes matches, ordering, or exit status, and readers must accept an
absent or unknown `hint`.

The `no-ai` promise above is about agent-reachable commands: it does not
constrain a human running their own `confidant` CLI, where an operator-only
flag that no agent path can pass (`--for-operator`, the same mechanism as
`record show --for-edit`) may surface `no-ai` records as
`no_ai: "true" | "notes" | "false"` (#559).

## 13. Privacy

Plaintext lives only on trusted devices. Git remotes hold ciphertext once
milestone 2 ships. Agents send what they read to a hosted model provider;
the README states this and does not claim the provider stores nothing.

`no-ai` is a front-matter scalar with three values (`true`, `false`,
`notes`; anything else is `E_FRONTMATTER`) on person, note, interaction,
and deal records. On any other record type it is `E_FRONTMATTER`.
`no-ai: notes` is valid only on person records (else `E_FRONTMATTER`):
the person record itself stays visible to agents — pack fields like
birthday and cadence reach `find`, `context`, and MCP — while their notes
and interactions default to hidden. The default is inherited through any
front-matter reference to the person — `person:`, the `people/<id>/` folder
path, `with:` participants, or any other field whose value is the person's
record ID or a list of record IDs containing it (#270) — not just
`person:`. A child's explicit `no-ai: true` or
`false` overrides the inherited default; a fully hidden (`no-ai: true`)
person keeps the old all-or-nothing guarantee and cannot be overridden
visible. Sensitive detail that must stay hidden from AI goes in its own
note with `no-ai: true`, which already excludes it from
`find`/`allowlist`/`reindex` even when the person stays visible ("any
`true` wins"). An unreadable or missing person header fails closed when
stamping children (stamped `no-ai: true`); mixed-version writers from
before `no-ai: notes` must not rewrite `notes`-mode people or write
children under them. Quoted `"no-ai"` / `'no-ai'` are
that flag; any other key that normalises to `noai` is a typo and
uncleared. `no-ai` covers records and IDs, not free-text name mentions: a
body or comment that names a `no-ai` person by display name alone, with no
record ID, stays searchable. Catching name-only mentions can only ever be
best-effort, so treat `no-ai` as a records-and-IDs guarantee. In 0.1,
`confidant find` follows the section 12 allowlist:
content is returned only from the cleared set, findings are themselves an
allowlist, body lines that mention uncleared or malformed IDs are dropped
(a malformed body token never hides the whole record), front-matter
malformed IDs un-clear the record, a note, interaction, or deal requires
every ledger line that names it to be allowed (persons are not
uncleared by this rule), `person` / `org` / `deal` values (including
case variants) must be
record IDs, and `pkg-` IDs follow their openers. `context` in milestone 3
continues to honour `no-ai`.

`confidant record show <id> --for-edit` and `confidant note show <id>
--for-edit` are **operator-only** reads. They are never exposed over MCP,
and they decrypt `no-ai` records in full because the operator may edit
them. They are not agent-facing output and they do not widen the section 12
allowlist: who may read a record and who may *edit* it are separate
questions, and only the operator edits. `record edit` and `note edit` write
through the same pipeline as `record add`; a note edit cannot move a note
to another person.

That is a policy boundary in the CLI surface, not access control. An agent
that can run commands on this device, with this device's key material in
reach, can invoke the read directly — as it could decrypt the file itself —
and no MCP tool call can reach it, because the MCP tool list is a fixed
whitelist. `docs/threat-model-agents.md` states the same limit for the other
operator commands.

Changing a person's mode does not rewrite the records already written about
them: a stored header is refreshed the next time that record is written
(§4). Re-stamping them in the same commit as the person edit is not part of
0.1.

Agent-facing findings policy: a finding never surfaces a `no-ai: true`
person's name or other PII to agents — the warning is suppressed or
reduced to a code and a count (opaque record IDs only). For a
`no-ai: notes` person (visible person, notes default hidden), name and
date in a finding are fine; note bodies never are. Operator-facing
`check` output may still list opaque IDs.

## 14. Encryption (milestone 2)

This section makes the milestone 2 format changes from
`docs/crypto-design.md` §13 normative. The design doc keeps the rationale;
this section is the contract. Until the milestone 2 implementation lands,
`check` validates every vault under sections 1–13 only (unknown
front-matter keys are ignored, so `enc:` files parse structurally); the
rules below are enforced by milestone 2 readers. No code in `check`
enforces this section today: the `E_KEY_COMMITMENT` and `E_ENVELOPE`
finding codes below are reserved for milestone 2 readers, not emitted by
`check`.

An **encrypted vault** is a vault containing at least one record file with
an `enc:` envelope or any `keys/` tree at all (a `recipients.toml` manifest,
the operator certificate `keys/operator.toml`, or any `epoch` file — a
half-initialized `keys/` is encrypted, not plaintext, and must never fall
into the plaintext branch). Any other vault is a **plaintext vault** and is
validated under sections 1–13 exactly: the rules below never fire on it,
so plaintext vaults keep passing `check` unchanged. A `mode = "plaintext"`
declaration (§2) permits plaintext record writes only while the vault is
structurally plaintext; the structural definition governs — a
`mode = "plaintext"` declaration combined with an `enc:` envelope or any
`keys/` tree is `E_CONFIG`, and the declaration can never downgrade an
encrypted vault. `confidant init` hard-refuses a vault whose
`confidant.toml` declares `[crypto] mode = "plaintext"`; to upgrade such a
vault, delete the declaration and run `init`.

### Key identifiers

Two different identifiers share the words "key id"; they are not
interchangeable:

- A **recipient key id** names one recipient in a key manifest
  (`keys/<client>/recipients.toml`, wrapping file
  `wrapped/<recipient key id>.age`). It matches `[a-z0-9-]+`.
  `recovery` is reserved: the recovery wrapping is always
  `wrapped/recovery.age`, never a recipient entry.
- An **envelope key id** is the `key_id` header of one encrypted record:
  `<client_id>/e<epoch>` (for example `p-01M3TC5H00MPJG000000000000/e3`,
  `vault:shared/e1`), pointing at the client data key and epoch that
  encrypted it.

(Agent scope documents name a third identifier, the **agent key id**
(for example `agent-transcriber-01`), which authorizes a scope. It lives
with the agent, never in the vault, and is never a wrapping target.)

`client_id` is the record owner's key holder: for `p`, `n`, and `i`
records, and for `d` records with a `person` field, the person's `p-…`
id; for `o` records, for `d` records with no `person`, and for `e`
records, the reserved id `vault:shared` (issue #62). The alias-lookup key uses the reserved id
`vault:lookup`. Reserved `vault:` ids are never person ids and never
appear as ledger subjects.

### Manifest v2

Key manifests live at `keys/<client>/recipients.toml` — a `p-…` id for a
person, `keys/vault/` for the reserved `vault:lookup` id, `keys/shared/`
for `vault:shared` — with the Ed25519 signature alongside as
`recipients.sig`. Wrapped data keys live in
`wrapped/<recipient key id>.age` for the current epoch and
`wrapped/<recipient key id>.e<epoch>.age` for retained older epochs.

`recipients.toml` carries `[[commitments]]`: one `{epoch, commitment}`
(hex) key commitment for every retained epoch. The commitment binds data
key, vault id, client id, and epoch:

```
HMAC-SHA256(data_key,
            "confidant-key-commit-v1" ‖ len(vault_id) ‖ vault_id
            ‖ len(client_id) ‖ client_id ‖ le64(epoch))
```

(lengths are 8-byte little-endian; `‖` is concatenation).

`vault_id` is bound in the signed manifest bytes and is not stored in the
file itself, binding the manifest to the vault. The signed bytes are, in
order:

```
"confidant-manifest-v2" ‖ len(vault_id) ‖ vault_id
‖ len(client_id) ‖ client_id ‖ le64(epoch) ‖ le64(seq)
‖ the exact recipients.toml bytes
```

(lengths are 8-byte little-endian; `‖` is concatenation). `recipients.sig`
is the 64-byte Ed25519 signature over these bytes. `seq` must not fall
below the reader's off-vault high-water mark for that
`(vault_id, client_id)`: a manifest with a lower `seq` is stale and is
refused even when its signature verifies.

A manifest may parse without `[[commitments]]`, but a reader refuses to
use any epoch the verified manifest carries no commitment for,
fail-closed (`E_KEY_COMMITMENT`).

### Writer certificates (delegated signing)

This subsection is the design revision for issue #779, answering Silas's
review of 2026-10-27 (signed — Silas). It is design only: no
implementation lands under it until #779 is answered, Frank gives
explicit OK at merge, and the implementation states **needs outside
audit before public launch**. The operator key is the root; a writer
certificate delegates manifest re-signing and git-commit signing only.
It never authorizes decryption by itself, and it never grants device
enrollment, writer grant/revoke, recovery rotation, root rotation, or
shred — those verbs are root-only by construction (see the field-level
rule below for why a writer cannot smuggle them in through a manifest).

#### Certificate format

Writer certificates live in the vault, so a fresh clone can verify a
writer-signed artifact using only the off-vault anchor plus the
in-vault cert:

```
keys/writers/<writer_id>.toml
keys/writers/<writer_id>.sig
```

`writer_id` matches `[a-z0-9-]+` (the same filename/principal rationale
as recipient key ids). A `writer_id` is never recycled: a writer revoked
and later re-granted gets a new id, so revocation history can never be
confused with a new grant.

```toml
[writer]
writer_id = "writer-marigold-vm"
label = "Marigold VM"
sign_pubkey = "<64 hex chars>"
age_recipient = "age1…"  # optional
issued_at = "2026-10-29"
expires = "2026-11-28"
seq = 1

[scope]
clients = ["p-01M3TC5H00MPJG000000000000"]
types = ["note", "deal"]
verbs = ["record.add", "ledger.append"]
```

Rules:

- `sign_pubkey` is the writer's Ed25519 signing key. `age_recipient`
  is its optional X25519 decryption identity. The two are separate on
  purpose: a writer that only appends ledger entries or re-signs
  manifests must not automatically decrypt every client. A certificate
  authorizes signing; decryption still requires a manifest wrapping for
  that client, exactly as for any other recipient.
- `issued_at` and `expires` are strict `YYYY-MM-DD` (UTC), parsed with
  the same strictness as agent-scope expiry in `docs/crypto-design.md`
  §7: a malformed date is a hard error, never "unexpired". The dates
  form an **ordered interval**, checked as follows. `issued_at` is
  effective at 00:00 UTC on that date and `expires` is effective at
  00:00 UTC on that date (exclusive), so a cert is in its window
  exactly when `issued_at <= now < expires` against the verifier's
  clock. The ordering rule is `issued_at < expires` and
  `expires - issued_at <= 30 days`, and a certificate whose lifetime
  exceeds 30 days fails verification. There is **no clock-skew
  allowance**: the verifier's clock is authoritative, and a reader
  with a wrong clock fails closed rather than widening the window.
  The ordering rule (`issued_at < expires`, lifetime bound) is a
  well-formedness check and **fails verification outright everywhere,
  including history re-verification** — a reversed interval
  (`issued_at >= expires`) is malformed, not merely expired, so it
  cannot slip through the history path where the expiry window is
  deliberately not re-checked. The window check itself
  (`issued_at <= now < expires`) applies only to **new acceptance**
  (see Verification order, step 8, and the SSH commit-signing
  section): a future-issued cert (`issued_at > now`) fails new
  acceptance, and an expired cert (`now >= expires`) fails new
  acceptance. A window failure within
  minutes of a 00:00 UTC boundary is the one case where a wrong
  system clock is the likely cause, and the diagnostic for such a
  failure must say so (`doctor` carries the same hint) — the hint
  never widens the window. Short lifetimes are the offline
  revocation-freshness model (see below): there is no online check.
- `seq` is the certificate version for this `writer_id`: 1 on first
  issue, +1 on every re-issue (including root rotation). Re-issued
  versions supersede older ones for new acceptance, but older versions
  stay in git history for history resolution (below).
- `[scope]` is a new writer-scope type, not an extension of
  `confidant-scope-v1`: the agent scope's `read`/`write` capabilities
  mean decryption/content access, and conflating them with signing
  authority would make both harder to audit. `clients` is an explicit
  list of client ids — there is no `"all"` wildcard for writers (a
  writer that may touch every client is root-equivalent in breadth;
  enumerate). `types` uses the agent-scope type vocabulary
  (`docs/crypto-design.md` §7). `verbs` is a **closed set**: exactly
  `record.add`, `record.update`, `ledger.append`. An unknown verb, an
  unknown type, or a malformed client id fails the whole certificate's
  verification — it is never ignored. `keys.init_client` is
  deliberately **not** a writer verb: initializing a client means
  signing its first manifest, and the field-level rule below refuses
  any writer-signed manifest with no previous verified manifest, so a
  first manifest is root-only by construction.
- `keys/writers/<writer_id>.sig` is the 64-byte Ed25519 signature over
  the domain-separated bytes, signed by the **operator** root key:

```
"confidant-writer-cert-v1" ‖ le64(len(vault_id)) ‖ vault_id
‖ the exact cert TOML bytes
```

  (lengths are 8-byte little-endian.) A cert transplanted from another
  vault does not verify, and a forged cert fails closed. The cert
  digest is the SHA-256 hex of the exact cert TOML bytes as committed;
  it pins the exact cert version a signature was made under (see
  signer binding).

Certificate-version resolution: cert versions are resolved
**causally, in the order links are accepted**, not against a global
maximum across the working tree and git history. The normative rule
is in "Causal, ordered validation of newly introduced ancestry"
below: a per-writer cert-`seq` high-water starts from the seed
(off-vault checkpoint and/or acceptance attestation, if any) and
advances only as each link in causal order is accepted, so a
legitimate renewal inside a newly introduced range never makes its
own earlier links look stale. A working-tree cert older than the
high-water resulting from its ancestry walk is stale and is refused
for new acceptance. For re-verification of a historical manifest,
the verifier resolves the exact cert version pinned by that
manifest's signer fields, from git history if superseded.

#### Signer binding in the manifest

`recipients.toml` gains three optional fields, inside the signed TOML
bytes, so stripping or swapping them breaks the manifest signature:

```toml
signer = "writer:writer-marigold-vm"
signer_cert_seq = 1
signer_cert_digest = "<64 hex chars>"
```

- A missing `signer` means `operator` (all existing manifests verify
  unchanged). A present `signer` must be exactly
  `writer:<writer_id>`, and it requires both `signer_cert_seq` and
  `signer_cert_digest`.
- `signer_cert_seq` must equal the `seq` of the cert version whose
  SHA-256 digest equals `signer_cert_digest`. This is what stops a
  re-issued cert with a wider scope from being swapped under an old
  signature: the old signature pins the old cert version, and a
  verifier that cannot resolve that exact version refuses the
  manifest.
- The manifest signature domain stays `confidant-manifest-v2` and the
  signed-byte construction is unchanged (the exact `recipients.toml`
  bytes are already part of the signed bytes). The signer binding is
  therefore a manifest-TOML schema addition, not a new signature
  domain — but the vault format change as a whole is a minor bump, not
  a patch (see Format minor and reader gate below).

#### Field-level rule: what a writer may change in a manifest

This is blocker (1) of the 2026-10-27 review. Manifests carry the
per-epoch key commitments and the recipient set. If a writer could sign
any manifest, it could change recipients or commitments, which is
device enrollment by another name, and "root-only by construction"
would not hold. The rule below is checked against the previous
verified manifest **before the signature even matters**: a manifest
that fails it is refused even if the writer's signature verifies. The
signature is still verified before any acceptance or decryption — the
field rule is about refusal, not about trusting unsigned data.

The previous verified manifest is the highest-`seq` verified manifest
for the same `(vault_id, client_id)` already accepted by the reader; a
fresh clone verifies history in `seq` order to establish it.

A writer-signed manifest is accepted only if **all** of the following
hold against that previous verified manifest:

- There **is** a previous verified manifest. A writer-signed manifest
  with no previous verified manifest is refused outright. The first
  manifest for a client is signed by the operator or recovery key
  only. (This is also why `keys.init_client` is not a writer verb.)
- The recipient map is **identical** (parsed-value equality): the same
  key ids, each with the same `age_pubkey`, `label`, and `scope_ref`.
  Adding, removing, or modifying any recipient entry — including a
  `label` or `scope_ref` tweak, which is a recipient change, not a
  cosmetic one — is refused.
- The `[[commitments]]` list is **identical** (same entries, same
  order, same commitment hex values).
- The signed-bytes `epoch`, `vault_id`, and `client_id` are identical.
  Only a root-signed manifest may change the epoch (rotation) or the
  recipient/commitment set (enrollment, revocation, rotation).
- The only fields that may move are `seq` (strictly greater than the
  previous verified `seq`; see Concurrency for the equal-`seq` rule)
  and the signer fields (`signer`, `signer_cert_seq`,
  `signer_cert_digest`), which may change only from `operator` to a
  writer, or between writers, or back to `operator` on a root re-sign.
  Any other field added, removed, or changed is refused.

In short: a writer re-signs an otherwise-identical manifest at a higher
`seq`. That re-signing is the writer's attestation for its write, and
it cannot smuggle a recipient or commitment change with it.

The commit carrying a writer-signed manifest is part of the same
acceptance check, under the commit authorization rule below. The
manifest path does not carry its own copy of that rule: verification
step 6 points to it.

#### Commit authorization rule: every writer-signed commit

Signature verification only **identifies** the writer. This rule
decides whether a writer-signed commit is **allowed**, and it runs on
**every** new writer-signed commit, with or without a manifest
change. A commit that verifies as `writer:<id>` but never meets this
rule is refused. Without it, a writer could sign a manifest-free
commit — a `ledger.append`-only commit, or one quietly editing
another client's records — and the manifest-scope check would never
run, breaking the containment the design is built on ("one agent host
leaks, revoke one writer").

For each commit being accepted, in order:

- Resolve the cert in effect **at that commit**: for a new commit,
  the cert version resolved under certificate-version resolution
  above; for a historical commit, the exact cert version pinned by
  the cert set at that commit in git history. The scope used is that
  cert's scope, as pinned — never a later, wider re-issue, and never
  the working-tree cert when history says otherwise. The cert must
  verify against the anchor chain at that commit (see Recovery
  rotation and historical verification below); a cert that cannot be
  resolved or verified refuses the commit.
- Enumerate the commit's changed paths from its diff. For a merge
  commit signed by a writer, the commit is checked against **each**
  parent: the diff against every parent must pass independently, and
  a failure against any parent refuses the commit. (Refusing
  writer-signed merge commits outright would also satisfy this rule,
  but it is not required; per-parent checking is the chosen rule.)
- Classify **every** changed path (adds, modifications, deletions,
  renames, mode changes). A rename is classified as a deletion of
  the old path plus an addition of the new path, each of which must
  pass independently. A mode change is classified as a modification
  of that path and passes only under the modification rule below.
  Any path that cannot be classified refuses the commit (fail
  closed). Writers should **rebase rather than merge**: a merge
  that pulls in an operator change to `keys/` or `confidant.toml`
  is refused against the writer's own parent (see below), so a
  merge-based workflow routinely fails where a rebase succeeds.

A changed path is allowed only in one of these classes:

- **Record addition.** A new record file belonging to a scoped client
  and a scoped record type, under the `record.add` verb. A record
  file is a file whose location and front matter identify it as a
  record for exactly one client (per the vault layout in §1/§2) of a
  type in the cert's `types`. A path that cannot be mapped to exactly
  one client and one type is unclassified.
- **Record modification.** A change to an existing record file for a
  scoped client and scoped type, under the `record.update` verb.
  The modification is classified from **both images**: the
  pre-image (the file as it stands at the parent commit, or at
  each parent for a merge commit) and the post-image (the file
  as it stands at this commit) must each independently classify
  to the **same** scoped client **and** the same scoped type,
  using each image's own location and front matter. If either
  image cannot be classified, or the two classifications differ
  in client or in type, the commit is refused: a writer scoped
  to client A and type `note` cannot edit an A note's front
  matter to move it to client B, or to an unscoped or different
  type, and have the move pass as a modification of its own
  record. A change whose pre-image and post-image carry
  different record ids is not a modification at all: it is
  classified as a deletion plus an addition, and the deletion
  refuses it (below). `record.add` can never modify or delete an
  existing record, and no writer verb deletes a record file: any
  deletion of a record file is refused.
- **Ledger append.** A change to a ledger file that adds only new
  lines at the end, each line for a scoped client, under the
  `ledger.append` verb. Ledger appends are append-only: editing or
  deleting any existing line refuses the commit, and a mode change
  to a ledger file is refused (it is not an append). "For a
  scoped client" means **every affected client** of the line is
  in the writer's scope, under the semantic classification in
  "Ledger affected clients" below — the primary id alone never
  suffices.
- **Manifest re-sign.** A change to a manifest's signed bytes and
  signature for a client (`recipients.toml` and `recipients.sig`
  under `keys/<client>/`) is allowed only when it is exactly the
  writer-signed manifest accepted under the field-level rule in the
  same commit, for the same client. Any other manifest change — a
  different client, an `epoch` move, a change to the client's
  `wrapped/` files, a recipient or commitment change outside the
  field-level rule — is refused under that rule, not here. A
  writer re-sign never changes the epoch or re-wraps keys; those
  are root-only changes.

Everything else fails closed, including: unclassified paths; anything
under `keys/` other than the manifest re-sign class above (certs in
`keys/writers/`, `keys/writers/revoked.toml`, operator/recovery
material, `keys/operator.toml`, `keys/recovery-recipients.toml`,
recovery checkpoints, acceptance attestations — a writer commit
touching `keys/writers/` is refused); `confidant.toml`; manifests
outside the field-level rule; and spec, pack, config,
documentation, or any other file. A commit with no classified
changes at all (an empty or metadata-only writer commit) is refused:
a writer signature must attest to an allowed change.

**Ledger affected clients.** A ledger line's effect is not bounded
by the file it lands in, so path classification alone cannot
authorize it. Every appended line is classified **semantically**:
its affected set is every client whose effective state the line
changes — every client the line references, and every client whose
derived state, canonical identity, alias resolution, balance
assertion, or touchpoint counts the line folds into. Every
affected client must be in the writer's scope (and, where the
classification names a record, that record's type must be in
scope too, determined from the record file's location and front
matter at that commit). If any affected client cannot be
determined, the line is unclassified and the commit is refused.

How the affected set is extracted depends on the verb:

- **Core verbs** (§6) have fixed classifications. `alias ID …`:
  affected is `{ID}` alone (the HMAC value names no client).
  `merge FROM into TO`: affected is `{FROM, TO}` — the target's
  effective state gains the source's whole history, and the
  source's canonical identity changes, so authorizing only the
  primary id would let a writer scoped to A change unscoped B's
  state. Both ids must be in scope, and the existing
  same-prefix/same-type rule still applies: a cross-type merge
  is refused regardless of scope. `stage DEAL-ID …`: affected is
  the owning client of the deal record named (the client the
  deal file maps to at that commit). `balance ID …`: affected is
  the owning client of the record named. `touch P-ID …`:
  affected is `{P-ID}` plus the owning client of every record
  id named in the line's arguments (`note:NOTE-ID` and any
  other id-valued argument); `src:` provenance and free-form
  kind tokens name no client and contribute nothing.
- **Id-shaped tokens are always references.** Extraction scans
  every argument of the line — positional arguments and pair
  values alike — for tokens matching a client or record id
  pattern. Any such token contributes its owning client (for a
  record id, the client its record file maps to; for a client
  id, itself), even in a position the verb calls free-form
  (for example a stage name that happens to be id-shaped). An
  id-shaped token whose owner cannot be determined — no
  record file at that commit, or a well-formed id with no
  client — makes the line unclassified. HMAC values
  (`hmac:HEX`) are not ids and are excluded from this scan;
  they carry no client reference.
- **Pack-defined verbs** are allowed for a writer-signed append
  only if the owning pack declares, in its manifest, how to
  extract the verb's affected clients: which argument positions
  or pair keys name client or record ids, and whether
  referenced record ids contribute their owning client. The
  declaration is part of the pack's contract, checked like any
  other manifest claim. A pack verb with no affected-clients
  declaration, a declaration that cannot be evaluated against
  the line as written, or a line whose effects the declaration
  does not cover, fails closed for writer-signed commits. A
  verb that is neither core nor in an enabled pack
  (`E_UNKNOWN_VERB`), or that belongs to a registered pack
  that is not enabled (`W_PACK_ORPHAN`), likewise fails
  closed for writers: its effects cannot be classified under
  an enabled pack. Root-signed appends are unaffected by this
  rule — the operator may append any verb; the check engine
  still validates the line's grammar.

History uses the same classification, with the cert pinned at
that commit: a historical ledger line is re-classified from the
line as committed and the record files as they stood at that
commit, not from the working tree.

History uses the same rule, with the cert pinned at that commit,
alongside the expiry and clock rules in Verification order: a
historical writer-signed commit is re-verified against the scope it
was signed under, not against a later cert version. The enumeration
of changed entries from a commit diff is an implementation detail;
the rule — every writer-signed commit, every path, fail closed — is
normative.

Worked example (schematic; the point is the refusal, not the bytes).
Previous verified manifest for client `p-A`: `seq = 4`, recipients
`{laptop, phone}`, commitments for epoch 3. Candidate writer-signed
manifest: `seq = 5`, recipients `{laptop, phone, attacker}`,
commitments unchanged, `signer = "writer:writer-marigold-vm"` with a
matching cert binding, and a signature that verifies under the
writer's cert key. **Refused.** The recipient set moved, so the
field-level rule fires before the valid signature matters, and no
decryption or acceptance follows from it. The same refusal applies to
a candidate that changes a commitment hex, drops a recipient, edits a
`label`/`scope_ref`, or moves the epoch — each is a root-only change
wearing a writer signature.

#### Verification order

For a writer-signed manifest, in order (any failure refuses, fail
closed, no key material or plaintext in the error). Steps 2–5 and 7
distinguish two modes, and the distinction is normative: **candidate
head** (a manifest being accepted as new, including every commit in
newly introduced ancestry — see the acceptance checkpoint below) and
**historical link** (a manifest already accepted, being re-verified as
the previous state of a chain or for read/decrypt). The high-water
check in step 7 and the expiry window in step 8 apply to candidate
heads only; they never apply to historical links. The field-level
rule, cert ordering, revocation seq rule, signature, and commit
authorization apply in both modes, with the cert pinned at the
commit for historical links.

1. Parse the manifest TOML.
2. Resolve the previous verified manifest for `(vault_id, client_id)`;
   none exists → refuse (writer-signed first manifest). The previous
   manifest is verified as a **historical link** first: its
   field-level rule, cert binding, revocation seq rule, signature,
   and commit authorization are re-checked under history rules, but
   the step-7 high-water check and the step-8 expiry window are
   **not** applied to it. A chain is walked in `seq` order to
   establish the previous verified manifest; each link is verified
   as history, and only the candidate at the end is checked as a
   candidate head. This is what makes reopening and advancing a chain
   possible after a higher `seq` has been accepted: the `seq = 11`
   link in a chain already accepted up to `seq = 12` verifies as
   history, while a fresh candidate at `seq = 11` offered as a new
   head after `seq = 12` is refused by step 7.
3. Field-level rule against the previous verified manifest.
4. Cert resolution and binding: the cert version pinned by
   `signer_cert_seq`/`signer_cert_digest` must exist and must verify
   against the operator key. The cert **ordering** rule
   (`issued_at < expires`, lifetime bound) is checked here and fails
   verification outright in both modes — a malformed cert cannot
   slip through history re-verification. For a new head, the anchor
   is the current off-vault anchor; for a historical manifest, the
   anchor is the operator key that was the anchor at that manifest's
   commit, chained through the recovery-signed operator certificate
   and, across a recovery rotation, through the recovery checkpoint
   chain (see Root rotation and Recovery rotation below) — rotation
   must not retroactively invalidate history.
5. Revocation seq rule (below). This is a different mark from the
   step-7 high-water: the revocation rule decides, per writer and
   client, whether a given `seq` survives a revocation, and it
   applies in both modes. The step-7 mark decides whether a `seq` is
   a rollback of the reader's accepted head, and it applies to
   candidate heads only.
6. Commit authorization rule (above) for the carrying commit. This
   step points to that rule; it does not carry its own copy. The
   scope check is the commit authorization rule: the writer's cert
   scope (clients, types, verbs, as pinned by the cert digest)
   covers the client, and every changed path in the carrying commit
   passes that rule.
7. Signature: `recipients.sig` verifies under the cert's
   `sign_pubkey` over the `confidant-manifest-v2` signed bytes. For
   a **candidate head only**, `seq` must also be at or above the
   reader's off-vault high-water mark for `(vault_id, client_id)`;
   a candidate below that mark is a rollback and is refused. The
   high-water check is scoped to the candidate head: it is never
   applied to a previous or historical manifest in the chain, and
   never to re-verification of already-accepted history.
8. Expiry and cert window for **new acceptance only**: a manifest
   accepted as a new head requires `issued_at <= now < expires`
   against the verifier's clock at acceptance time, with no skew
   allowance (see the certificate format rules). Expiry is **not**
   re-checked when re-verifying already-accepted history for
   read/decrypt — otherwise every writer-signed manifest would stop
   verifying 30 days after issuance and history would become
   unreadable. This read/write split holds only for ancestry already
   covered by a recorded acceptance checkpoint or an acceptance
   attestation seed (see below): on a fresh clone with neither,
   there is no such coverage, so the whole introduced chain is new
   acceptance and every manifest in it gets the wall-clock check.
   Expiry gates new writes, the revocation seq rule gates history,
   and a suspected-leaked key is retired for history only by
   revocation, never by expiry alone.

Operator- and recovery-signed manifests keep the existing verification
path unchanged and are exempt from the writer field-level rule: changing
recipients, commitments, or epoch is the root's job.

#### Acceptance checkpoint: newly introduced ancestry vs previously accepted history

Checking the verifier's clock only for a newly accepted tip does not
establish when its ancestors were accepted. On a fresh clone, an
attacker holding an expired broad-scope writer key and a currently
valid narrow-scope key could backdate a broad-scope commit, place a
valid narrow-scope commit at the tip, and have the forged ancestor
treated as "history" that avoids the new-head expiry check. The
distinction that closes this is not tip-vs-ancestor: it is
**previously accepted vs newly introduced**, recorded in a trusted
acceptance checkpoint.

Each reader keeps an off-vault acceptance checkpoint next to
`trust.toml` (alongside the existing `manifest-seq.toml` and
revocation high-water marks; same trust and permissions as the
anchor — on the trusted device, never in the vault, never trusted
from an in-vault copy). The checkpoint records, for the vault: the
accepted tip commit id, the per-client manifest `seq` high-water at
that tip, the `revoked.toml` file `seq` high-water, and the per-writer
cert `seq` high-water (see certificate-version resolution: recording
it here is what stops a force-push from dropping history and
resurrecting a superseded cert version on a fresh clone). The
checkpoint is updated **only after** a fetched chain verifies in
full; partial verification never updates it, and a checkpoint must
never move backwards — a checkpoint naming a tip or high-waters
below the reader's current ones is ignored and the chain is treated
as newly introduced.

On any fetch, clone, or merge, ancestry is partitioned by
reachability from the recorded accepted tip:

- **Previously accepted history** is every commit reachable from the
  recorded accepted tip. It is verified under history rules: the
  expiry window is not re-checked, the step-7 high-water check is
  not applied, and certs are pinned at their commits — but the
  field-level rule, cert ordering, revocation seq rule, signature,
  and commit authorization rule still apply, with the cert pinned at
  each commit.
- **Newly introduced ancestry** is every commit not reachable from
  the recorded accepted tip — including the tip itself, any commit
  above it, and any side ancestry a merge or fetch brings in that was
  not previously accepted. Every such commit is **new acceptance**,
  whether or not it is the tip: it gets the full candidate-head
  checks (wall-clock cert window, causal ordered cert validation,
  field-level rule against its previous verified manifest, commit
  authorization, revocation, and the step-7 high-water check). A
  forged ancestor under a valid tip is therefore refused on
  introduction, not waved through as history.

A fresh clone has no checkpoint, so it has no previously accepted
history: the whole introduced chain is new acceptance, and every
manifest and writer-signed commit in it gets the wall-clock check —
unless an acceptance attestation seed applies (proposal, see
below), in which case commits reachable from an attested tip are
history and only commits above the attested tip are new acceptance.
This narrows the earlier reading of decision (a) ("on a fresh clone,
the tip is new acceptance; only ancestors are history"): that
reading holds only once a checkpoint or attestation seed exists.
With neither, there are no ancestors that have been accepted, and
none may be assumed. If a reader's checkpoint is lost or
deleted, the next fetch is treated the same way — a fresh
introduction, with full new-acceptance checks for the whole
chain and a diagnostic naming the missing checkpoint — never
a silent downgrade to history verification. Once the chain
verifies, the checkpoint is recorded and later fetches use
the partition above.

#### Acceptance attestation (PROPOSAL — for review, not settled)

> **Status: proposal.** This subsection is a design proposal
> developed for review at Frank's direction. Its security details
> are **not approved**: the trust and rollback rules below need the
> same scrutiny as the rest of this design, and no implementation
> may treat them as settled until Silas and Frank approve this
> subsection on re-review. Every genuinely open choice is marked
> **Open question** below. Until approval, a reader behaves exactly
> as if no attestation existed (whole introduced chain is new
> acceptance), and an attestation file present in a vault is never
> trusted by a reader that does not implement this subsection.

The problem this proposal addresses is the one Silas identified in
re-review: a fresh clone has no off-vault checkpoint, so the whole
introduced chain is new acceptance, the wall-clock cert window is
checked on every writer-signed commit in it, and certs live at most
30 days — legitimate writer history older than 30 days is refused
on a new device ("history dies every 30 days"). The checkpoint
partition cannot help a fresh reader, because the checkpoint is
off-vault by design. The proposal is a **trust seed a fresh reader
can check without prior state**: a root-signed, in-vault
attestation over an accepted tip and the high-waters at that tip,
so the reader can treat commits reachable from the attested tip as
history — accepted by root — and apply full new-acceptance checks
only above it. The forged-ancestor attack must stay closed under
it: an attestation never authorizes anything above its tip, and a
forged commit above the newest attestation is still new acceptance
and is refused.

**Format.** Attestations are committed files, one per attestation:

```
keys/acceptance-attestations/<seq>.toml
keys/acceptance-attestations/<seq>.sig
```

```toml
seq = 1
prev_attestation_digest = "<64 hex chars or empty for the first attestation>"
tip_commit = "<40 hex chars>"
last_verified_manifest_seq = { "p-01M3TC5H00MPJG000000000000" = 12, "vault:shared" = 7 }
revoked_file_seq = 3
revoked_manifest_high_water = { "writer-marigold-vm" = { "p-01M3TC5H00MPJG000000000000" = 12 } }
writer_cert_seq_high_water = { "writer-marigold-vm" = 1 }
```

Rules:

- `seq` is monotonic across the vault, starting at 1, +1 per
  attestation. Each attestation after the first binds
  `prev_attestation_digest`, the SHA-256 hex of the exact
  previous attestation TOML bytes. The digest binds the chain
  of attestations, not the git ancestry: an attestation's
  `prev_attestation_digest` must equal the digest of *some*
  verified attestation with `seq - 1` present in the ancestry
  being verified. The first attestation has an empty digest.
  An attestation whose digest matches no `seq - 1`
  attestation is unchained and is not a candidate seed (see
  selection below). A gap in `seq` is a chain break, not a
  silent skip.
- `tip_commit` is the accepted tip commit at attestation time.
  `last_verified_manifest_seq` is, per client, the highest
  verified manifest `seq` at that tip. `revoked_file_seq`,
  `revoked_manifest_high_water`, and
  `writer_cert_seq_high_water` are the revocation and cert
  high-waters at that tip, with exactly the meanings they have
  in the acceptance checkpoint and the recovery checkpoint.
  An attestation carries **no validity window**: it does not
  expire, and no `attested_at` date (if recorded by an
  implementation for diagnostics) is ever a trust input. Its
  trust comes from its signature, its ancestry, and its
  high-waters — never from time. **Open question:** whether an
  `attested_at` diagnostic field should be part of the format
  at all, or omitted to avoid any reader mistaking it for a
  validity bound.
- The attestation is signed by the **operator** root key or the
  **recovery** key — the current anchor keys — under its own
  domain:

```
"confidant-acceptance-attestation-v1" ‖ le64(len(vault_id)) ‖ vault_id
‖ the exact attestation TOML bytes
```

  (lengths are 8-byte little-endian, as for certs and
  revocations.) A **writer key can never sign an attestation**:
  an attestation whose signature verifies only under a writer
  key, or under any key that was not an anchor key at the
  commit where the attestation file appears, is not a
  candidate seed. An attestation signed by a retired operator
  key verifies through the same anchor-at-commit chain as a
  historical cert (operator certificate at that commit
  verified against the recovery key then in force, and
  across a recovery rotation through the recovery checkpoint
  chain): rotation does not retroactively invalidate an
  attestation written while its signer was an anchor, but a
  retired key never counts as current authority, and an
  attestation written *after* its signer retired — claiming
  authority at a commit where the anchor is a different key —
  does not verify. An attestation signed by a key that was
  never an anchor fails closed as a seed. **Open question:**
  whether a recovery-key signature alone should be sufficient
  for an attestation, or whether operator-key signatures
  should be required and recovery-key signatures treated as
  valid only when they also carry a recovery checkpoint (the
  proposal as written allows either anchor key, matching
  `revoked.toml`).
- Attestation files are append-only in the same sense as
  recovery checkpoints: adding a new `<seq>.toml` is the only
  permitted change. Modifying an existing attestation file
  destroys that file's candidacy as a seed (its digest and
  signature no longer match the bytes as committed), and
  deleting one does not hide it — selection scans ancestry
  (see below), so a deleted file still counts if it is in
  the ancestry. A writer-signed commit touching
  `keys/acceptance-attestations/` is refused under the commit
  authorization rule: attestation files are under `keys/`,
  and no writer class permits them.
- A recovery checkpoint counts as an attestation for seeding
  purposes: a verified recovery checkpoint (domain
  `confidant-recovery-checkpoint-v1`, signed by the new
  recovery key) seeds history below its `tip_commit` with the
  high-waters it carries, under the same selection and
  rollback rules. No separate attestation file is needed for
  a rotation to seed fresh-device recovery. The recovery
  checkpoint's `seq` is its own chain and is not compared
  with attestation `seq`s; only its tip and high-waters enter
  seed selection.

**Who writes attestations, and when.** Operator devices write an
attestation whenever they accept a chain that advances the
accepted tip — that is, when recording or updating the off-vault
acceptance checkpoint after a full verification, the device also
commits an attestation over the new tip and its high-waters, in a
root-signed commit. **Open question:** whether on-acceptance
writing is mandatory or best-effort. As written it is mandatory
for a device that wants fresh readers to verify its history:
the staleness consequence is explicit — if no device writes an
attestation, fresh readers get no seed and old history is
refused after 30 days, exactly the pre-proposal behaviour.
Attestation writing is never required for an existing reader
with a checkpoint, and a device that never writes one harms
only fresh readers, never existing ones. Commit churn is the
cost: every tip advance that is attested adds a root-signed
commit. **Open question:** whether a stated cadence (for
example, at most one attestation per day, or only when the tip
advances by more than one writer-signed commit) should bound
that churn, and what the freshness consequence of a cadence
bound is for a fresh reader arriving between attestations.
Until the cadence question is answered, the proposal states
the on-acceptance rule and records the churn cost plainly,
rather than silently assuming a cadence.

**Selection: how a fresh reader picks a trustworthy attestation.**
Selection runs over the ancestry of the candidate head being
verified, never over the working tree alone and never over an
uncommitted file: an attestation file present only in the
working tree never seeds anything. In order:

1. **Collect.** Every attestation file (and every recovery
   checkpoint) present in any commit reachable from the
   candidate head.
2. **Verify as candidates.** A file is a candidate only if its
   signature verifies under an eligible anchor signer at the
   commit where it appears (above) — for a recovery checkpoint,
   under the new recovery key, per its own section — its domain
   and `vault_id` binding are correct, its format parses, its
   chain is unbroken back to its first entry through verified
   entries in the same ancestry (for an attestation, the
   `seq` chain via `prev_attestation_digest` back to `seq = 1`;
   for a recovery checkpoint, its own checkpoint chain via
   `prev_checkpoint_digest`), a `prev_attestation_digest`
   matching no `seq - 1` attestation disqualifies it, and
   its `tip_commit` exists in the ancestry. A shallow clone
   whose fetched ancestry does not contain the full chain
   back to `seq = 1` therefore has no candidate seed: the
   chain cannot be checked from the fetched history alone,
   and the reader falls back to fresh-introduction checks
   rather than trusting a truncated chain. A file failing
   any of these is not a candidate: it seeds nothing, and the
   reader records a diagnostic naming the file. A bogus
   attestation file planted by push access therefore cannot
   lower a seed — it is simply ignored — and cannot by
   itself fail the head. (A *validly signed* attestation that
   is internally inconsistent — for example a `seq` gap in
   an otherwise root-signed chain — is different: it is a
   root-side inconsistency, and the reader fails closed
   rather than seeding from an older attestation while a
   newer root-signed one exists but cannot be trusted. See
   rollback rule 4 below.)
3. **Applicability.** A candidate applies to this head only
   if its tip is an ancestor of, or equal to, the candidate
   head. A candidate whose tip is on an unmerged branch, or
   is a descendant of the head (the head predates the
   attestation), does not seed this head: it is ignored for
   this verification, neither raising nor lowering the seed.
4. **"Newest".** In linear history there is one dominant
   candidate: the applicable candidate whose tip is a
   descendant of every other applicable candidate's tip.
   That candidate is the seed. Where history forks and no
   single candidate's tip dominates — two attestations on
   divergent branches, both ancestors of a merge head — the
   seed is the **set** of applicable candidates, not one of
   them: history is the union of commits reachable from any
   seed tip, and the seed high-waters are the
   component-wise maximum across the set (per-client
   manifest `seq`, `revoked.toml` file `seq`, per-writer
   revoked manifest high-waters, per-writer cert `seq`).
   Taking the maximum is safe for rollback in every
   component: a higher high-water never re-admits a revoked
   writer or a superseded cert. Two candidates with the
   same `seq` but different bytes are a root fork: both are
   validly signed and neither dominates. The reader fails
   closed on the fork **unless** a higher-`seq` attestation,
   chained to one of the variants, resolves it — that
   attestation's tip and high-waters supersede both
   variants, and the unchained variant is ignored. An
   unresolved root fork is a diagnostic, not a silent
   choice: the operator's remedy is to re-attest at a higher
   `seq` over the intended tip.
5. **Seeding.** Commits reachable from any seed tip are
   history. Only commits above every seed tip (not
   reachable from any seed tip) are new acceptance, and
   are validated by the causal ordered walk below, starting
   from the seed high-waters. An attestation never
   authorizes new acceptance above its tip.

**Rollback prevention.** The seed is a floor, never a ceiling
that can be lowered:

1. **Monotone high-waters.** The ordered walk above a seed
   starts from the seed high-waters (see Causal, ordered
   validation below). A link below the floor at its point
   in the walk is refused. Seed high-waters never decrease
   within a verification: the walk only advances them.
2. **Older attestation replay.** Presenting an older
   attestation (lower high-waters, earlier tip) while a
   newer verified attestation exists in the same ancestry
   cannot roll anything back: selection takes the dominant
   candidate or the set maximum, and the older attestation
   contributes nothing the newer one does not already cover.
   An attacker with push access but no root key cannot
   forge a newer attestation, and replaying an older
   genuine one is inert because the newer one is also in
   the ancestry being verified.
3. **Checkpoint combination.** The reader's off-vault
   acceptance checkpoint, if present, is combined with the
   attestation seed by component-wise maximum, exactly as
   for forked attestations: the seed for this verification
   is the max of the checkpoint's recorded high-waters and
   the attestation seed's, and history is the union of
   commits reachable from the checkpoint tip and from any
   seed tip. An attestation below the reader's existing
   checkpoint is ignored for every component where the
   checkpoint is ahead; it never moves the checkpoint
   backwards. After a full verification, the reader records
   a new checkpoint at the component-wise maximum of the
   old checkpoint, the seed, and the high-waters resulting
   from the walk above the seed. If the checkpoint was
   lost, the attestation seed alone seeds the verification,
   and the checkpoint is re-recorded from it — that
   re-recording is the recovery path the proposal exists
   for, and it is safe only because the seed is
   root-signed.
4. **No silent fallback to an older seed.** If a newer
   attestation exists in the ancestry but fails candidate
   verification (bad signature, broken chain, unresolvable
   signer), the reader does **not** silently seed from an
   older attestation and proceed: it fails closed with a
   diagnostic naming the failed attestation. Falling back
   would let a tampered or truncated newer attestation
   hide behind an older seed with lower high-waters. The
   only exception is the root-fork resolution in selection
   step 4, where a higher chained attestation explicitly
   supersedes the fork.
5. **Conflicts with the chain.** If the chain above a seed
   tip contains a manifest `seq` below the seed's
   per-client high-water, a `revoked.toml` file `seq`
   below the seed's `revoked_file_seq`, or a cert `seq`
   below the seed's per-writer cert high-water at the
   point where the walk reaches it, the chain is refused:
   the seed and the chain disagree, and the disagreement
   is a rollback, not a stale seed. The seed is never
   adjusted down to match the chain.
6. **No seed, no weakening.** When no attestation or
   recovery checkpoint verifies as a seed, the reader
   behaves exactly as before this proposal: the whole
   introduced chain is new acceptance, with a diagnostic
   naming the missing attestation. An attestation is an
   additional seed, never a fallback that weakens an
   existing check, and a reader that does not implement
   this subsection ignores attestation files entirely and
   keeps the old behaviour.
7. **Force-push limit, stated plainly.** An attestation in
   history that a force-push drops is gone for a fresh
   reader, together with the history it covered: the
   reader cannot distinguish a vault whose attestation
   was dropped from a vault that never had one, and
   verifies the fetched chain as a fresh introduction.
   Existing readers are protected by their off-vault
   checkpoints (a dropped attestation cannot lower a
   recorded checkpoint). This proposal does not close
   the force-push gap for fresh readers; it closes the
   30-day history gap only for history that is still
   present with its attestation.

**What the proposal must prove (test plan).** See
`docs/crypto-design.md` §12 item 29: a fresh clone of a vault
with a 60-day-old writer commit under a later attestation
verifies it as history; a backdated forged ancestor above
the newest attestation is refused; fresh-device recovery
across a rotation verifies through the recovery checkpoint
acting as seed; and the rollback-replay cases — older
attestation replay with a newer one present, attestation
below an existing checkpoint ignored, writer-signed
attestation refused as a seed, attestation on an unmerged
branch not seeding another head, and a root-forked `seq`
failing closed until re-attested. **Open questions for
review**, collected: the `attested_at` field; recovery-key
signatures alone vs operator-key required; mandatory
on-acceptance writing vs a cadence bound and its freshness
cost; and whether forked attestations should fail closed
even when a set-maximum seed is well-defined (the proposal
allows set-maximum seeding; a stricter reading would refuse
any fork outright). Until Silas and Frank answer these, the
attestation subsection is a proposal, not a rule an
implementation may build on.

#### Causal, ordered validation of newly introduced ancestry

This subsection replaces the earlier "highest cert `seq`
across the working tree and git history" resolution rule
for newly introduced ancestry. That rule made offline
catch-up across a cert renewal fail for no security
reason: an offline reader fetching legitimate sequential
commits signed under cert `seq = 1` and then renewed cert
`seq = 2` judged the first link against the maximum `seq`
visible anywhere — including the later cert — so the
first link looked stale even though both certs were
currently valid. The fix is to validate in causal order
and advance the high-water as each link is accepted.

**Seed.** The walk starts from a seed: the reader's
off-vault acceptance checkpoint, an acceptance attestation
seed (proposal above), and/or a recovery checkpoint seed,
combined by component-wise maximum as defined in the
attestation subsection. The seed supplies, per writer, a
starting cert-`seq` high-water (0 when no seed records one:
no floor), plus the per-client manifest `seq`, revocation,
and cert high-waters at the seed tips. Commits reachable
from any seed tip are history and are not walked here;
every other commit in the introduced range is walked, in
causal (topological) order, oldest first, from the seed
boundary outward. A fresh clone with no checkpoint and no
attestation seed has an empty seed: the walk starts at the
root of the introduced chain with floor 0, and the
wall-clock window is enforced on every link (see below).

**Per-link rule.** For each link in the walk, in order:

- The cert in force is the cert version **visible at that
  commit**: the cert file content at that commit in git
  history, for the writer that signed the link. If the
  link's manifest or signature pins a different cert
  version (`signer_cert_seq`/`signer_cert_digest`) than
  the cert file at that commit, the link is refused: the
  pin and the file must agree at the link, so a later
  re-issue can never be read back into an earlier link.
- The cert must verify: signature under the anchor chain
  at that commit (through the recovery checkpoint chain
  across a rotation, as for history), and the ordering
  well-formedness rule (`issued_at < expires`, lifetime
  bound) — ordering fails outright at every link,
  including history links. The expiry **window**
  (`issued_at <= now < expires` against the verifier's
  clock) is checked for every link **above the seed**:
  newly introduced links are new acceptance. For links
  at or below a seed tip the window is not re-checked;
  that is what the seed is for.
- **Staleness is judged against the high-water at that
  link, not the global maximum.** A link signed under a
  cert `seq` below the per-writer high-water in force
  when the walk reaches it is refused (rollback or
  superseded cert). A link signed under a cert `seq` at
  or above that high-water proceeds to the remaining
  checks. **Only on acceptance of the link** does the
  high-water advance to that link's cert `seq` (if
  higher). A link that fails any check advances nothing:
  a failed link poisons the walk, and no later link in
  the same range is accepted on the strength of a
  high-water the failed link would have set.
- **Revoked and expired certs mid-chain.** A link signed
  under a cert that is revoked in the revocation state
  in force at that link is refused as new acceptance,
  subject to the revocation seq rule: the seq rule
  preserves verification of already-accepted history
  at or below the revocation high-water, and does not
  authorize new acceptance above a seed by a revoked
  writer — a candidate head signed by a currently
  revoked writer is refused even if its manifest `seq`
  is at or below the high-water. A link signed under a
  cert that is expired **at acceptance time** and above
  the seed is refused even if the cert was valid when
  the link was written: the remedy is an attestation
  covering the link before expiry, or re-signing under
  a current cert. Expiry mid-chain is therefore not
  silently forgiven by causal order; causal order only
  stops a *renewal* from retroactively staling its own
  earlier links.
- **The candidate head.** The final link — the tip being
  accepted — is checked against the high-water resulting
  from its ancestry walk, including any renewal accepted
  earlier in the same batch. A working-tree cert older
  than that resulting high-water is stale and is refused,
  even if it is the highest cert in the working tree.
  This is the rule that replaces the global-maximum
  comparison: the walk's floor already incorporates
  every cert `seq` accepted in the range, so scanning
  the whole tree and history for a maximum adds nothing
  and is what broke catch-up. The force-push protection
  the global maximum used to provide now comes from the
  seed: an existing reader's off-vault checkpoint floor,
  or an attestation seed floor, stops a force-push from
  dropping history and resurrecting a superseded cert.
  A seedless fresh clone has no such floor — that limit
  is stated in the attestation subsection, not hidden
  here.
- **Merges.** Each parent's side is validated
  independently from the **shared** seed: a side's
  links are judged against the seed high-waters and
  the high-waters advanced along that side only, so a
  `seq = 2` accepted on one side does not make a
  `seq = 1` link on the other side stale. The merge
  commit itself is checked against the **maximum** of
  the parents' resulting high-waters: its cert `seq`
  must be at or above that maximum, and the merged
  high-water is the maximum of the parents' and the
  merge link's `seq`. The merge commit's commit
  authorization is checked against each parent, as
  before.

After the whole introduced range verifies, the reader
records (or updates) its off-vault acceptance checkpoint
with the final high-waters from the walk. A partial walk
never updates the checkpoint, and never seeds a later
verification.

Above a root-signed attestation the same walk applies
with the seed high-waters taken from the attestation:
the high-water starts from the attestation's recorded
values and advances link by link, and staleness at each
link is judged against the high-water at that link, not
against any later maximum — including the attestation's
own recorded maximum, which is the floor, not a ceiling
to be compared against from the start. See
`docs/crypto-design.md` §12 item 28 for the test plan:
offline catch-up across a cert renewal is accepted; a
link signed under `seq = 1` after `seq = 2` was accepted
in the same chain is refused; the same holds for a
fresh clone with no checkpoint; and the same walk above
an attestation seed starts from the attestation
high-waters.

#### Revocation, keyed to sequence (not time)

This is blocker (2) of the 2026-10-27 review. Revoking a writer must
not invalidate everything it ever signed (history would stop
verifying), and a wall-clock cutoff must not decide it (a compromised
host just backdates). The cutoff is a manifest `seq`.

`keys/writers/revoked.toml` is append-only and root-signed, with a
monotonic file `seq` and a signature alongside as `revoked.sig`:

```toml
seq = 3

[[revoked]]
writer_id = "writer-marigold-vm"
revoked_by = "operator"
manifest_seq_high_water = { "p-01M3TC5H00MPJG000000000000" = 12, "vault:shared" = 7 }
```

Rules:

- Entries are never removed, and a `writer_id` is never reused (see
  above). `revoked_by` records which anchor key signed the file
  version that added the entry: `"operator"` or `"recovery"`.
- `manifest_seq_high_water` maps each client id to the highest
  writer-signed manifest `seq` for that writer that the revoker had
  observed at revocation time. A client absent from the map means the
  revoker had observed no writer-signed manifest for that client — any
  later writer-signed manifest for that client is above the high-water
  and is rejected.
- `revoked.sig` is the 64-byte Ed25519 signature over:

```
"confidant-writer-revoked-v1" ‖ le64(len(vault_id)) ‖ vault_id
‖ the exact revoked.toml bytes
```

  It verifies against the operator **or** the recovery anchor key.
  Revocation is therefore signable by the operator or the recovery
  key, as the review confirms. A revocation signed by any other key
  fails closed.
- Acceptance rule: a writer-signed manifest for a client with
  `seq > manifest_seq_high_water[client]` is rejected; one with
  `seq <= manifest_seq_high_water[client]` keeps verifying (subject
  to every other check). Unpushed writer signatures above the
  high-water — including ones the revoker had never seen — are
  rejected once the revocation lands, which is the protection the
  high-water exists for.
- Rollback: readers keep an off-vault revocation high-water mark — the
  highest `revoked.toml` file `seq` seen — next to `trust.toml`
  (alongside `manifest-seq.toml`), updated on every sync/fetch. A
  `revoked.toml` with a file `seq` below that mark is refused, so
  restoring a pre-revocation revocation file cannot resurrect a
  revoked writer. The same history-based resolution that protects cert
  versions applies: the working-tree revocation file is never trusted
  over the history maximum.
- Survival across rotation: revocation high-waters (the `revoked.toml`
  file `seq` and every per-client manifest `seq` high-water) and cert
  `seq` high-waters are carried in every recovery-rotation checkpoint
  (see Recovery rotation below) and must survive the transition: a
  post-rotation revocation file with a lower file `seq` or lower
  per-client high-waters than the checkpoint records is refused, so a
  recovery can never reset a revoked writer.
- `keys writer revoke <id>` performs the append-and-sign above, and
  `doctor` reports one line per writer (cert `seq`, expiry, status
  `active` / `expired` / `revoked`, and, when revoked, the manifest
  `seq` high-water per client). `doctor` also warns when the last
  fetch is older than 30 days — the same window as the maximum cert
  lifetime, deliberately: a reader that has not fetched in longer than
  a cert can live cannot know about recent revocations, and must say
  so rather than verify quietly.

#### Root rotation (Q6)

Rotation re-issues every writer cert under the new operator key, with
scope preserved exactly: a rotation re-issue must not widen (or
narrow) a scope — a scope change is a separate grant with its own cert
`seq` bump, never smuggled inside a rotation. New certs are issued
before the new operator certificate is pinned; the overlap window —
first new cert issued to new operator cert pinned — is at most one
cert lifetime (30 days). Once the new operator certificate is pinned,
old-root certs stop verifying **for new acceptance**. Pre-rotation
history keeps verifying through the anchor-at-commit chain **while
the recovery key is unchanged**: the operator certificate at a
historical commit verifies against the recovery key, which does not
rotate in an operator rotation, so a historical writer-signed
manifest resolves its cert against the operator key that was the
anchor when it was signed. The review's "old-root certs stop
verifying once the new operator cert is pinned" is therefore read as
a new-acceptance rule, not a history invalidation — without that
qualification, every rotation would break history verification, the
same failure the seq-keyed revocation rule exists to avoid. This
anchor-at-commit reasoning holds **only** for operator rotation. A
recovery rotation retires the recovery key itself, so historical
operator certificates signed by the retired recovery key need the
recovery checkpoint chain below; without a checkpoint they lose
their anchor, and that loss is fail-closed, not silently repaired.

#### Recovery rotation and historical verification

`recover` and `keys shred` rotate the recovery identity and remove
the old recovery key from every current anchor set (see
`docs/crypto-design.md` §4/§9). The anchor-at-commit chain in Root
rotation therefore cannot carry history across a recovery rotation
on its own: historical operator certificates signed by the retired
recovery key — and the writer certs those operator certs signed —
would lose their anchor. The bridge is a **recovery checkpoint**,
created as a mandatory part of every recovery rotation.

Checkpoint format. At rotation time, before the old recovery key is
retired or destroyed, a checkpoint is committed to the vault:

```
keys/recovery-checkpoints/<seq>.toml
keys/recovery-checkpoints/<seq>.sig
```

```toml
seq = 1
prev_checkpoint_digest = "<64 hex chars or empty for the first checkpoint>"
old_recovery_pubkey = "<64 hex chars>"
new_recovery_pubkey = "<64 hex chars>"
tip_commit = "<40 hex chars>"
last_verified_manifest_seq = { "p-01M3TC5H00MPJG000000000000" = 12, "vault:shared" = 7 }
revoked_file_seq = 3
revoked_manifest_high_water = { "writer-marigold-vm" = { "p-01M3TC5H00MPJG000000000000" = 12 } }
writer_cert_seq_high_water = { "writer-marigold-vm" = 1 }
```

Rules:

- `seq` is monotonic, starting at 1, +1 per rotation. Each checkpoint
  (after the first) binds `prev_checkpoint_digest`, the SHA-256 hex
  of the exact previous checkpoint TOML bytes, so checkpoints form a
  verifiable chain. A checkpoint whose `seq`, `prev_checkpoint_digest`,
  or history range does not chain correctly is refused.
- The checkpoint is signed by the **new** recovery key. A signature
  by the retiring recovery key before it is shredded may be present
  as an additional co-signature for readers that already trust the
  retiring key, but it does not substitute for the new-key
  signature: a checkpoint carrying only a retiring-key signature
  cannot be verified by a fresh-device reader holding only the new
  phrase, and does not count for historical verification there.
  The new-key signature is what binds the old recovery pubkey to
  the stated history range, and the signature domain is:

```
"confidant-recovery-checkpoint-v1" ‖ le64(len(vault_id)) ‖ vault_id
‖ the exact checkpoint TOML bytes
```

  A checkpoint signed by the operator key, a writer key, or any
  other key fails closed, and a forged checkpoint (bad signature,
  wrong domain, wrong `vault_id`, or a history range that does not
  cover the commits it is used to verify) is refused. The old
  recovery key never counts as current authority by virtue of a
  checkpoint: a checkpoint authorizes **historical** verification
  only, for commits at or below the checkpoint's `tip_commit` and
  manifest `seq` range. It never authorizes new acceptance above
  its tip. As a **seed** it partitions commits at or below its tip
  as history, exactly as an acceptance attestation does (see
  Acceptance attestation below) — the "never" is about new writes
  above the tip, not about seeding history below it.
- The checkpoint binds the old recovery pubkey to a specific history
  range: `tip_commit` is the tip commit at rotation time and
  `last_verified_manifest_seq` is, per client, the highest verified
  manifest `seq` at that tip. To verify a historical operator
  certificate signed by the retired recovery key, the reader walks
  the checkpoint chain from the current anchor recovery key back to
  the checkpoint binding that old pubkey, and verifies the operator
  certificate against the bound old pubkey for commits within the
  checkpoint's range. Writer certs signed by that operator key
  verify through the same chain, with the cert pinned at the
  historical commit.
- Revocation and cert high-waters survive: the checkpoint carries
  the `revoked.toml` file `seq`, every per-client manifest `seq`
  high-water, and every per-writer cert `seq` high-water at rotation
  time. Readers carry them forward across the transition, and a
  post-rotation revocation file or cert set with lower marks than
  the checkpoint records is refused. A recovery rotation can never
  reset a revoked writer or resurrect a superseded cert version.
- Rotation is not complete until the checkpoint is committed.
  `recover` and `keys shred` must create and commit the checkpoint
  before retiring the old recovery key, and must refuse to complete
  the rotation if the checkpoint commit fails. A vault whose history
  contains a recovery rotation with no checkpoint for the retired
  key is handled by the no-checkpoint rule below, not by inventing
  one.

Fresh-device recovery. On a fresh device the old recovery key is
unavailable to sign anything, so the reader trusts only the
checkpoint(s) present in git history at the recovery commit, signed
by the **new** recovery key derived from the entered (current)
phrase: the phrase-derived recovery pubkey must match the
checkpoint's `new_recovery_pubkey`, and the checkpoint signature
must verify under it. The checkpoint is then trusted for the reason
stated above: it is signed by the recovery identity the operator
holds, it binds a specific old pubkey to a specific history range,
and it never grants new-acceptance authority. The reader does **not**
re-pin the retired key as an anchor, and does not treat the absence
of a checkpoint as permission to trust the old key.

No checkpoint, fail closed. When no checkpoint exists for a retired
recovery key — a pre-checkpoint rotation, a lost checkpoint file, or
a checkpoint whose chain does not verify — the reader fails closed
for new acceptance of any artifact depending on that key, and for
history it refuses to verify the dependent history with a clear
diagnostic naming the missing checkpoint and the retired key id. It
does not restore the old key as current authority, does not fall
back to an in-vault copy of the old pubkey, and does not silently
treat the history as operator-signed. The operator's remedy is to
re-create the binding from a device that still holds the retiring
identity, or to accept that the affected history cannot be verified
on that reader.

#### SSH commit signing (Q4, in scope for this design)

Commit trust today is based on the anchor keys' SSH fingerprints. If
writers only signed manifests, the agent host would still need the
operator key to make trusted commits, so the copied root from #729
could not be retired and the compromise math ("one agent host leaks →
revoke one writer") would not hold. Q4 is therefore part of this
design, not a separate filing.

- The writer's Ed25519 signing key doubles as its SSH commit-signing
  key. No new signed bytes are needed for commits: git SSH signing
  already signs the commit object; what changes is the verification
  source.
- Allowed signers are **derived at verification time from verified
  in-vault certs**, never read as authority from a committed
  allowed-signers file in the vault (anyone with push access could add
  their own key to such a file). A locally derived file outside the
  vault (for example under `.confidant/`) is a cache only and is
  re-derived on use.
- Derivation, per writer with a cert verifying against the anchor:
  principal is exactly `writer_id`; key is the cert's `sign_pubkey`
  as an SSH Ed25519 key; `valid-after` is `issued_at` at 00:00 UTC;
  `valid-before` is `expires` at 00:00 UTC. `valid-before` in the
  derived allowed-signers is **defense in depth, not the boundary**:
  git checks it against the commit's committer date, which the
  signer controls, so a leaked key from an expired, unrevoked cert
  could backdate a commit inside its window and pass `ssh-keygen`
  verification. The boundary is the verifier's clock: for new-commit
  and new-head acceptance, expiry is checked as
  `issued_at <= now < expires` against the verifier's clock at
  acceptance time, with no skew allowance, and a commit signed after
  expiry but backdated inside the window is refused as a new head.
  On a fresh clone the tip is new acceptance and gets that
  wall-clock check; ancestry is partitioned by the acceptance
  checkpoint or an acceptance attestation seed (see above), so a
  fresh clone with neither checks the whole introduced chain, not
  just the tip. Expiry limits new writes; only revocation retires
  a suspected-leaked key for history. For new-commit acceptance the cert must be unexpired
  under that clock check and the writer unrevoked: revoked writers
  are dropped from the current derivation entirely, so a new commit
  signed by a revoked writer fails verification. Historical commits
  verify against the cert set at that commit, by the same
  history-resolution rule as manifests, with the cert pinned at the
  commit and the expiry window not re-checked (cert ordering still
  fails outright — see the certificate format rules).
- Every writer-signed commit, with or without a manifest change,
  runs the commit authorization rule above. SSH signature
  verification identifies the writer; the authorization rule decides
  whether the commit is allowed. A manifest-free writer-signed
  commit that passes signature verification but fails authorization
  is refused, exactly as a manifest-carrying commit would be.
- Dual use is safe by domain separation: an SSH signature is over a
  git object, a manifest signature is over `confidant-manifest-v2`
  domain-separated bytes — the same key never signs the same bytes
  under two meanings. Operator-signed commits keep verifying under the
  existing anchor-key path.
- Migration consequence: after the first writer cert is granted to the
  host holding the copied operator key and that copy is retired, the
  host's commits verify as `writer:<id>`, never as operator. The
  copied root is retired, not duplicated.

#### Concurrency

Two writers can race to the same manifest `seq` and fork. The git
branch is the arbiter: the first pushed commit wins, and the loser
re-signs on top. Verification enforces it:

- A candidate manifest whose `seq` equals the current head `seq` but
  whose bytes differ from the head manifest (different signer, or any
  other difference) is rejected as a fork (reserved code
  `E_MANIFEST_FORK`). It is never auto-merged: two writer-signed
  manifests at the same `seq` are two different claims about the
  vault's head, and merging them would need a root decision.
- A candidate at an equal `seq` with byte-identical manifest bytes
  (and signature) is an idempotent re-push and is accepted.
- The loser re-signs on top: it fetches the new head, re-runs the
  field-level rule against that head, and signs at a `seq` strictly
  greater than the head `seq`. The rule applies regardless of signer:
  operator-vs-writer and writer-vs-writer forks are handled the same
  way, and an operator-signed head at `seq + 1` resolves a fork
  unilaterally (the operator is root).

#### Format minor and reader gate

This is a **minor** format change, not a patch. Existing
operator-signed vaults verify unchanged, but an older binary cannot
verify the first writer-signed manifest and would read it as tampering.
Two gates, in order, stop that misreading:

1. **Spec minor.** Writer certificates exist only in vaults at the
   spec minor that carries this section, and such a vault declares
   that minor version. `keys writer grant` refuses on a spec-0.1
   vault, so no conforming spec-0.1 vault ever contains
   `keys/writers/` (a spec-0.1 vault that does is non-conforming and
   is refused by new readers with `E_CONFIG`). A pre-gate reader
   meeting a writer-capable vault therefore refuses the vault with
   `E_SPEC_UNSUPPORTED` — the clear error it already emits for a
   spec version it does not implement — before it ever attempts
   manifest verification.
2. **Minimum reader version.** Within that minor, `confidant.toml`
   `[crypto]` gains exactly one defined key,
   `minimum_reader_version`: the CLI version (semver) that first
   implements writer certificates, set at the first grant and bumped
   by any later writer-format change. (This section defines the key;
   the `[crypto]` table in §2 gains it when the spec minor is cut.)
   Readers check it **before** any manifest verification and refuse
   with the reserved code `E_READER_TOO_OLD` — naming the required and
   actual CLI versions — when their CLI version is lower. A reader
   must never attempt manifest verification on a vault above its
   minimum and report the result as tampering.

#### Migration

- Existing operator-signed manifests and commits keep verifying
  unchanged. Granting the first writer cert does not re-sign existing
  manifests.
- The migration path for #729: grant the first cert to the host that
  currently holds a copied operator key, then retire that copy under
  the #711 custody model (secure deletion on the agent host; the root
  is never copied to an agent host by default thereafter). The first
  writer re-sign of a head runs the field-level rule against the
  operator-signed head: recipients and commitments identical, `seq`
  +1, signer flips `operator` → `writer:<id>`.
- A fresh clone verifies a writer-signed manifest with only the
  off-vault anchor and the in-vault cert (plus git history for a
  pinned superseded cert version). Errors and logs carry codes and
  writer/client ids, never key material or plaintext.

### Operator certificate (fresh-device recovery)

`keys/operator.toml` holds the operator Ed25519 pubkey for fresh-device
recovery:

```toml
[operator]
pubkey = "<64 hex chars>"
```

`keys/operator.sig` is the 64-byte Ed25519 signature over the
domain-separated bytes:

```
"confidant-operator-cert-v1" ‖ 0x00 ‖ vault_id ‖ 0x00 ‖ pubkey_bytes
```

signed by the **recovery** Ed25519 key at `init`. On a device with no
`trust.toml` (lost device, no config backup), `recover` verifies this
certificate against the phrase-derived recovery pubkey and rebuilds the
trust anchor from the verified operator pubkey. The signature binds the
pubkey to the vault id: a certificate transplanted from another vault
does not verify, and a forged certificate (signed by any other key)
fails closed. Vaults initialized before this file existed have no
certificate; fresh-device `recover` on such vaults still requires a
config backup.

### Recovery recipient history

`keys/recovery-recipients.toml` records every recovery age recipient the
vault has ever wrapped data keys to:

```toml
recipients = [
  "age1…",
]
```

It is append-only. Each `recover` and each `keys shred` (both rotate the
recovery identity) appends the retired and the new recipient; the file
may be absent on a freshly `init`ed vault, in which case the only known
recipient is the trust anchor's `recovery_age_recipient`. Readers union
the working-tree copy with **every historical version from git**
(oldest-to-newest states, deduplicated), so a later commit cannot remove
an entry. The set is used to refuse a new device recipient that reuses a
retired recovery key (see `ever_seen_pubkeys`): re-enrolling one would
let the retired recovery key open a shredded client's history. The file
is unsigned — it feeds a denylist, so a union that is only ever too large
is safe.

### `keys verify-recovery` (read-only)

`confidant keys verify-recovery [--phrase-file <path>]` checks a saved
recovery phrase without changing anything. The phrase arrives via stdin
or `--phrase-file` only, never as an argument, and is parsed with the
same BIP39 validation as `recover`. It needs no device key, no operator
key, no clean tree, and works on an enrolled device or a fresh one.

A match requires all of:

- if `~/.config/confidant/trust.toml` exists, both its Ed25519
  `recovery_pubkey` and its X25519 `recovery_age_recipient` match the
  phrase. An existing anchor that disagrees is a mismatch: the command
  never falls back to the `keys/` tree in that case;
- if `keys/operator.toml` exists, its certificate verifies against the
  phrase-derived recovery pubkey (the check a fresh-device `recover`
  depends on);
- the phrase identity trial-unwraps the current-epoch
  `wrapped/recovery.age` for every initialized client except
  `vault:lookup`, whose key is device-only. Unwrapped keys are held in a
  zeroizing type and dropped immediately; they are never returned,
  logged, or cached.

Exit 0 on a full match. Failures exit 1 with a stable code:
`E_RECOVERY_RETIRED` (the derived recipient is recorded in
`keys/recovery-recipients.toml` but is not the anchor's current one — the
copy must be destroyed because it still opens history),
`E_RECOVERY_MISMATCH`, `E_RECOVERY_MALFORMED`, and `E_RECOVERY_UNWRAP`.
Usage errors exit 2. The command writes nothing: no config dir, no
`keys/`, no git, no keychain.

With `--json`, the report carries `outcome` plus `checks` (`anchor`,
`recipient`, `cert`, and `unwrap` per client). It never includes the
words, a word position, derived keys, or fingerprints. A malformed
phrase's word-position hint is printed to stderr only. This verb is
CLI-only: it is not an MCP tool and no skill authorizes an agent to pipe
a phrase into it.

### Envelope

An encrypted record is one file: an outer front matter header plus a
base64 body holding the ciphertext of the full inner record (front matter
with `name:`, plus body). The outer header carries exactly `id`, `type`,
`no-ai`, `enc`, `key_id` (the envelope key id), and `nonce`
(base64 of the 24-byte AEAD nonce). `no-ai` stays plaintext so
`find`/`context` fail closed without keys; its value is `true`, `false`,
or `notes` (`notes` only on person records — §13). `enc` names the AEAD
(`xchacha20poly1305`).

`E_ENVELOPE` is the keyless structural check — no keys and no plaintext
needed. It rejects: duplicate header keys; unknown header keys; a missing
required header (`id`, `type`, `no-ai`, `enc`, `key_id`, `nonce`); an
`enc` other than `xchacha20poly1305`; a nonce that is not 24 bytes; bad
base64; and an envelope key id that is not `<client_id>/e<epoch>` (the
client is the part before the final `/e`, the epoch an ASCII decimal
`u64`).

The routing question — is the key id's client the right key holder for
this record under the client id rule above? — cannot be answered
keylessly: for notes, interactions, and deals the record's `person` is
inside the ciphertext. Routing is enforced at decrypt time as the
header-consistency rejection below, not as an `E_ENVELOPE` finding.

Header consistency is enforced alongside decryption: `id` must equal the
record ULID bound in the AAD, the envelope key id's client must equal the
client the record is decrypted for, the envelope key id's epoch must
equal the AAD epoch, and `type` must map to exactly one purpose
(`person`→`profile`, `note`→`note`, `interaction`→`interaction`,
`org`→`org`, `deal`→`deal`, `edge`→`edge`). Any inconsistency fails closed: decryption
is refused and the record is withheld. This is a decrypt-time command
error (`Error::Header`); it has no stable finding code yet.

### AAD

Every encryption binds all of the following components, in this order,
each prefixed with its 8-byte little-endian length: `confidant1`,
`vault_id`, record ULID, `client_id`, relative path, `purpose`, key epoch
as ASCII decimal, then the outer header as five separate components —
`id`, `type`, `no-ai` as the text `true`, `false`, or `notes`, `enc`, `key_id` —
in that order, not the raw front-matter text. The `nonce` is the AEAD
nonce and is not part of the AAD. Any mismatch fails authentication: no
silent misbinding.

### Shred

`keys shred p-A` destroys A's client key and, in the same signed commit,
deletes every edge file naming A from the working tree. Edge deletion is
fail-closed: if any edge cannot be read (skipped or refused envelope, or
a load finding under `edges/`), or any edge's ends cannot be determined,
shred refuses before destroying the key. The shred output warns:

> Edges that named this person were deleted from the working tree, but
> earlier versions in git history remain readable with the shared key.

Edges live under the shared key (`vault:shared`, see §14's client-id
rule), so deleting the working-tree copy does not make earlier git
versions unreadable — they stay readable to anyone holding the shared
key. A shredded participant's own touchpoints stay in the ledger as
opaque-id lines (the ledger is not rewritten by shred). Cleaning a
`with:` list up on shred is deferred.
